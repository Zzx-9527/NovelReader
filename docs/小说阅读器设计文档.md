## 1. 项目定位

### 1.1 一句话定位

**「静读」是一款完全离线、无广告、无需注册的本地小说阅读器 —— 导入自己的 TXT 文件，进度永不丢失。**

### 1.2 目标用户

- 手上存有大量 TXT 小说、习惯用手机长时间阅读的用户
- 受够了阅读 App 的广告、会员墙、强制登录与书架同步的用户
- 对隐私敏感、不愿让"我在读什么"被上传的用户
- 鸿蒙 NEXT 用户（生态内好用的本地阅读器稀缺）

### 1.3 三条产品原则

1. **零联网**：工程内不存在任何网络请求代码，书与进度 100% 留在本机
2. **零注册零广告**：打开即用，没有账号、会员、推荐位
3. **进度绝不丢**：这是阅读器的生命线 —— 换字号、重启、切后台都必须回到原处

### 1.4 差异化设计（避免"又一个套壳阅读器"）

| 差异化点 | 具体做法 |
|---|---|
| 编码自动识别 + 可手动纠正 | TXT 圈子里 GBK/GB18030 极常见，多数阅读器只认 UTF-8。本 App 自动探测，判错时可**一键换编码重解析**而不必重新导入 |
| 大文件不崩 | 全书**不整读入内存**：导入时流式分章只记录字节偏移，阅读时按偏移随机读该章 |
| 进度与排版解耦 | 进度只记「章节序号 + 章内偏移 + 百分比」，**绝不存页码**；换字号后仍回到同一句话 |
| 分页结果可缓存 | 排版参数生成指纹 `layoutKey`，按指纹缓存断点；切回同一章不重算 |
| 数据可迁移 | 书籍与进度可导出备份，用户自己保管 |

## 3. 页面详解

> 状态图例：✅ 已完成 · 🟡 部分完成 · ⏳ 待做 · ❌ 已砍

### P0｜根页面（底部导航）
**状态：✅ 已完成**（`pages/Index.ets`）

**目标**：承载 Tabs，并且**作为唯一可靠的刷新时机来源**

**页面结构**
```
Index (@Entry)
├── Tabs { 书架 / 统计 / 我的 }
└── 书架状态由本页的 BookShelfViewModel 持有
```

**⚠️ 这一页存在的真正理由：`onPageShow` 只对 `@Entry` 页面触发**

书架页是普通 `@Component`，它**拿不到** `onPageShow`。
第一版把"从阅读页返回后刷新进度"挂在书架页的 `onPageShow` 上 —— 那个钩子**从来没被调用过**，
表现是"阅读进度只有重启 App 才同步"。这个 bug 花了两轮才定位。

**结论（已定案）：刷新时机必须由根页面显式驱动**

```ts
// Index（@Entry）—— 只有它拿得到这两个可靠时机
onPageShow(): void {
  ShelfRefreshRegistry.refresh();     // 从阅读页返回 / App 回到前台
}
// Tabs
.onChange((index: number) => {
  if (index === 0) {
    ShelfRefreshRegistry.refresh();   // 切回书架
  }
});
```

书架页在 `aboutToAppear` 里把 ViewModel 注册进 `ShelfRefreshRegistry`，
`aboutToDisappear` 里注销。这是一个**受控的全局引用**，不是事件总线：只有一处使用，随页面销毁即清空。

**为什么不给每个 Tab 内容用 `TabContent.onWillShow`**
参考项目（HabitFlow）用的是它，`@since 12`，覆盖 first-time display / tab switching /
page switching / 前后台切换。本项目**也用它**是更好的方案（覆盖面最全），
但当前实现先用根页面驱动把功能跑通；迁移到 `onWillShow` 是下一轮的重构项（见 §6 风险表）。

### P1｜书架页
**状态：✅ 已完成**（`pages/BookShelfPage.ets` + `views/bookshelf/`）

**目标**：一眼看到"我在读什么、读到哪了"，三步内开始阅读

**页面结构（从上到下）**
1. ✅ 标题行：`书架` + 网格/列表切换 + 排序 + 导入按钮
2. ✅ 导入/重解析进度文案（大文件解析时必须可见，否则像卡死）
3. ✅ **继续阅读卡片**：最近在读且未读完的一本，显示"读到第 N 章 / 共 M 章"+ 进度条 + 继续按钮
4. ✅ 分组 chips（全部 / 各分组）
5. ✅ 书籍网格（3 列，封面 3:4）或列表
6. ✅ 空状态：`EmptyView` + 导入引导
7. ✅ 错误状态：`ErrorView` + 重试

**交互**
- ✅ 点击书籍 → 进入阅读页
- ✅ 长按书籍 → 动作菜单：开始阅读 / **换编码（正文乱码时用）** / 从书架移除
- ✅ 切换排序（最近阅读 / 导入时间 / 书名），选择记入 Preferences
- ✅ 网格/列表切换，选择记入 Preferences
- ⏳ 分组管理页（新建/重命名/排序）
- ⏳ 书名搜索

**两个关键设计**

| 决定 | 理由 |
|---|---|
| **封面用"书名首字 + 浅色底"占位** | TXT 文件没有封面；`Image` **不接受空字符串路径**（会抛错），所以不做无效分支。接入 EPUB 封面时替换这一处渲染即可 |
| **"换编码"放在长按菜单，而不是重新导入** | 自动探测不可能对每个 TXT 都准确。让用户手动指定编码后重建章节，比"删掉重新导入"省事得多 —— 这是 TXT 阅读器的刚需 |

**⚠️ 换编码的代价必须在点之前说清**
重新分章会触发 `chapter` 的外键 `ON DELETE CASCADE`，**连带删除该书全部书签/笔记**。
所以菜单标题里先写明数量：`重新分章会删除已有的 N 条书签/笔记`。
（当前是"告知后直接执行"，**没有二次确认** —— 书签功能上线后必须补上确认弹窗。）

### P2｜阅读页（核心页面 ⭐）
**状态：🟡 主体完成**（`pages/ReaderPage.ets` + `views/reader/` + `viewmodels/ReaderViewModel.ets`）

**目标**：正文阅读、翻页、跳章、沉浸式，且**进度永不丢**

**页面结构（Stack 分层，顺序即层级）**
```
第 1 层  正文 + 常驻底栏（最底）
         正文：章节标题是**正文的第一行**（加粗、字号 +2），读过去就滚走
               page 模式：只渲染当前页（标题只在本章第一页）；scroll 模式：标题+整章可滚
         常驻底栏：左=当前章节名，右=全书进度百分比，上方一条分隔线
第 2 层  翻页层（点击 + 滑动） ← 仅当 !menuVisible 且 !settingsVisible 且 pageMode !== 'scroll'
第 3 层  顶栏 / 底栏          ← 仅当 menuVisible，在翻页层之上
第 4 层  设置面板             ← 仅当 settingsVisible，上半透明热区 + 下半面板
```

> **目录不再是浮层**：已从"第 5 层抽屉 + 遮罩"改为**独立页面**
> `pages/ReaderCatalogPage`（目录 / 书签两个 Tab，左上角返回按钮）。
> 原因见 §5.5 的"目录为什么从抽屉改成独立页面"。

**⚠️ 常驻底栏必须在"第 1 层内部"与正文并列，不能做成 Stack 上的独立浮层**

放在同一层里，正文的 `layoutWeight(1)` 会自动得到"容器高 − 底栏高"；
做成独立浮层就得自己保证"正文高度 = 总高 − 底栏高"，一旦漏算，
**分页每页都会少排一行**，而且极难联想到是底栏造成的。

另外常驻底栏**不绑任何手势**：它压在正文底部，一旦绑了 `onClick`/拖拽，
按 `HitTestMode.Default`（阻塞兄弟节点）会把屏幕最下一条的
翻页点击与滚动拖拽整个吃掉 —— 表现是"最下面一条点不动也划不动"。
反过来说，正因为不绑手势，用户点到屏幕最底部时仍然**正常翻页**，这是想要的行为。

**⚠️ 常驻底栏必须"无条件渲染"，不能挂在 `if (error.length === 0)` 之下**

它的显隐会改变正文区高度 ⇒ 触发 `onAreaChange` ⇒ 重新分页 ⇒
而重新分页又会经过 loading/error 状态、可能再次改变显隐 ——
正是第 39 条那类"高度随条件变化导致分页抖动"的坑。
恒定显示换来高度恒定，代价只是出错时这里显示上一次的章节名。

**⚠️ 弹出式底栏"覆盖"常驻栏，不是"叠在它上面"**

见下方"弹出式底栏是覆盖"一节 —— 这里只强调结论：
菜单栏/设置面板都从**屏幕底部升起**把常驻栏整个盖住，**不给它们留底部 padding**。

**⚠️ 阅读页所有浮层栏一律用不透明的 `theme.bg`，不用 `theme.barBg`**

`barBg` 是半透明色（alpha 约 `F2`）。**阅读页的四个栏全部用不透明 `bg`**：
顶栏、菜单底栏、设置面板、常驻底栏 —— 它们弹出时下方都压着正文，
半透明会让正文文字从后面透出来，看起来像渲染错误。

> 本项目实测踩过：早期顶栏用 `barBg`、底栏用 `bg`，屏幕上出现
> "上面透、下面不透"的割裂感（顶栏标题上叠着正文的字）。
> 统一成不透明后观感才一致。

`barBg` 现在只用于**不透明容器内部**的小色块（如设置面板里未选中的字号胶囊），
那里下方是纯色面板、不存在文字透出的问题。

分隔线/文字色用 `theme.secondary`（**跟随阅读主题**，
不能用 `AppColor` 系统令牌，否则羊皮纸/夜间主题下会露出不搭的系统色）。

**⚠️ 沉浸式全屏：`setWindowLayoutFullScreen(true)` 是前提，`expandSafeArea` + 安全区 padding 是配套**

整个 app 采用沉浸式（内容铺满全屏、状态栏与手势条区域显示应用底色）。三件事缺一不可：

| 步骤 | 位置 | 作用 |
|---|---|---|
| ① `setWindowLayoutFullScreen(true)` | `EntryAbility.onWindowStageCreate` | **前提**：让窗口进入全屏布局 |
| ② `expandSafeArea([SYSTEM], [TOP, BOTTOM])` | 每个页面根节点 | **绘制范围**：背景铺到屏幕最边缘 |
| ③ 安全区 `padding` | 每个页面根节点 | **内容范围**：文字/按钮不钻到状态栏、手势条下面 |

**⚠️ 漏掉 ① 是最容易犯的错**（本项目实测踩过）：`expandSafeArea` 只是"**允许**延伸到安全区"，
窗口若仍是非全屏布局，内容区压根不含安全区 —— 此时页面里怎么写都没用，
表现就是"阅读页底栏永远悬在安全区上方、怎么调都贴不到底"。

**⚠️ ② 和 ③ 必须成对**：
- 只写 ② → 内容被状态栏/手势条盖住（点不灵）；
- 只写 ③ → 让出的那两条露出系统色，看起来像"上下各一条灰边"，沉浸式白做。

**⚠️ 底部安全区要用"紧邻它的那个栏"的颜色来填，不能只让外层背景透出来**

本项目实测踩过（书架页）：根节点写 `padding({bottom: safeAreaBottom})` +
背景 `bgPage`（浅灰），而紧邻的底部导航栏是白色（`bgCard`）——
于是最底下那一条显示的是**浅灰**，看起来像"导航栏没铺到底、下面多了一条灰边"。

正确做法：底部安全区用**独立占位**填成**导航栏同色**（`Index.ets` 里的
`if (safeAreaBottom > 0) { Row().height(safeAreaBottom).backgroundColor(bgCard) }`），
导航栏视觉上就自然延伸到了屏幕最底边。

**判据：安全区那条不是"空白"，而是"某个栏的延伸"** ——
先问"它紧挨着谁"，再用谁的颜色。顶部同理（状态栏上方紧邻的是页面标题区，
所以用 `bgPage` 即可）。

**安全区高度由 Ability 测一次、全局共享**：`EntryAbility.publishSafeArea()` 用
`getWindowAvoidArea()` 读出来（`AvoidArea.Rect` 单位是 **px**，必须 `px2vp()` 换算），
写进 `AppStorage`；页面用 `@StorageProp('safeAreaTop')` 订阅，值到位后自动重排。

> ⚠️ `@StorageProp` 的参数**写字符串字面量**，不用 `AppStateKey.SAFE_AREA_TOP` 常量：
> 该参数会被 ets-loader 在编译期解析成 key 名，对表达式形式的支持没有保证。
> 代价是 key 在两处重复，改的时候要一起改（`AppStateKey` 里已注明）。

**⚠️ 同一组件不要连续调两次 `.padding()`** —— ArkUI 里是**后者覆盖前者**，不是叠加。
本项目实测踩过：菜单层先写 `.padding({top})` 又写 `.padding({bottom})`，
顶部避让被静默吃掉（顶栏被状态栏盖住），而代码看起来"两处都写了"。
上下边距必须合并进同一次调用。

**⚠️ `READER_FOOTER_HEIGHT` 是"文字区高度"，底栏总高要动态加安全区**

底栏总高 = `READER_FOOTER_HEIGHT + safeAreaBottom`（见 `ReaderPage.footerTotalHeight()`），
用于底栏自身高度。安全区不能写死进常量 —— 各机型手势条高度不同（有的还没有）。

结构上：底栏外层钉死总高，内层文字行用 `layoutWeight(1)` 吃掉"总高 − 分隔线 − 手势条占位"
的余量，末尾再放一个 `safeAreaBottom` 的**显式占位**。
于是背景铺到屏幕最底边（沉浸式），而文字落在手势条上方（不打架）。

**⚠️ 弹出式底栏是"覆盖"常驻底栏，不是"叠在它上面"（用户实测反馈后改的）**

第一版让菜单层整体上移 `footerTotalHeight()`，结果是两条栏**上下堆叠**：
常驻底栏仍露在菜单下面，屏幕上同时出现两排信息，观感很乱。

正确行为是**覆盖** —— 从屏幕底部升起，把常驻底栏整个盖住。落地要点：

| 要点 | 做法 |
|---|---|
| 菜单层不再留底部 padding | 只让出**顶部**安全区 |
| 弹出栏自己涂满底部安全区 | 加 `safeAreaBottom` 属性，`padding.bottom = 12 + safeAreaBottom` |
| 背景必须**不透明** | 用 `theme.bg`，**不用**半透明的 `theme.barBg`（会让下层文字透出来） |
| 动画挂**各自的栏**上 | 顶栏 `translate({y: -TOP_BAR_HEIGHT})`、底栏 `translate({y: 80})` |

> ⚠️ 动画若挂在外层 `Column` 上，顶栏会跟着底栏一起**从下往上**滑，方向完全不对。
> 必须分别挂在 `ReaderTopBar` / `ReaderBottomBar` 上。

设置面板（`SettingsPanel`）同理：也从底部升起、也覆盖常驻底栏，同样走上面四条。

**两种底栏的分工（不要重复显示同一信息）**

| | 常驻底栏（`buildReaderFooter`） | 菜单底栏（`ReaderBottomBar`） |
|---|---|---|
| 出现时机 | **永远可见** | 仅当 `menuVisible`（从底部升起、**覆盖**常驻栏） |
| 内容 | 左=章节名；右=`页码 百分比` | 设置 + 进度条 + 上一章/下一章 |
| 职责 | **告知**（我在哪、读了多少） | **操作**（跳转、切章、调设置） |
| 背景 | 不透明 `theme.bg` | 不透明 `theme.bg`（覆盖式，**不能**半透明） |

**所有"告知类"信息只在常驻栏显示**：章节名、页码、全书百分比。
菜单栏早期也重复显示过这几项，已全部删掉 —— 它现在只剩操作。

页码（`5/16`）只有分页模式才有值；scroll 模式整章连续滚动，
没有"第几页"的概念，`ReaderState.pageText` 返回空串，常驻栏就不渲染它，
右侧只剩百分比。

**⚠️ 第 2 层和第 3 层的顺序是踩坑后改的**
第一版把点击分区**常驻**在 Stack 最上层，结果菜单弹出后它盖在顶栏/底栏之上把点击截走 ——
点中间等于又切换一次，菜单**弹出后无法收回**。
`if` 条件里必须有 `!this.state.menuVisible`，两块区域在任何时刻都只存在一个。

**⚠️ 第 2 层还必须在 scroll 模式下缺席（"阅读页划不动"的根因）**
那三个分区 `Column` 都绑了 `onClick`，按 ArkUI 的触摸测试规则
（`HitTestMode.Default`：自身响应 + **阻塞兄弟节点**），它们会把拖拽事件整个吃掉，
下层 `Scroll` 永远收不到滑动 —— 只有点击生效。
滚动模式下点击改由 `Scroll` 自己接管（单击整屏切菜单，短章节时正文下方空白也能点）。
**判据：任何绑定在 Stack 上层的手势层，都要问一句"它会不会把下层需要的拖拽吃掉"。**

### 5.5.1 目录页（`pages/ReaderCatalogPage`）

**⚠️ 目录为什么从抽屉改成独立页面**

第一版是"第 5 层抽屉 + 遮罩"，宽 78%、浮在正文之上。实测问题：

| 问题 | 独立页面如何解决 |
|---|---|
| 只占 78% 宽，1000+ 章的长目录翻找很憋屈 | 整屏宽，滚动区域更大 |
| 浮在正文上，容易误触到正文/翻页层 | 整页替换，没有下层可误触 |
| 只有一个列表，塞不下"书签" | 顶部两个 Tab：目录 / 书签 |

**版面**
```
‹ 返回        目录 | 书签
─────────────────────────
第27章: 暗害
第28章: 抱冰术          ← 当前章高亮（AppColor.brand）
...
```

**⚠️ 选章结果不走路由回传，走 `ReaderJumpRegistry` 登记表**

页面间传参有两条路，**都不能用**：

- `back(index, params)`：`index` 是**页面栈下标**，而栈深取决于用户从哪进来
  （Splash → Index → Reader → Catalog），写死数字非常脆；
- `back({ url, params })`：文档只承诺"回到该页、**不重建**"，
  **没有**承诺 params 会被目标页的 `getParams()` 取到。

所以沿用本项目已有的 `ShelfRefreshRegistry` 范式：静态登记表 + 页面主动领取。
目录页 `request(章, 偏移)` → `back()`；阅读页在 `onPageShow` 里 `consume()` 并跳章。

> ⚠️ `consume()` 必须**取走即清空**：`onPageShow` 在"App 从后台回来"时也会触发，
> 不清空的话用户切个后台再回来就会莫名又跳一次。

> ⚠️ 偏移的 **-1 语义要翻译**：登记表里 `-1` = "未指定，落到章首"；
> 而 `ReaderViewModel.switchChapter` 里 `-1` = "定位到**章末**"（上一章回退用）。
> 两者含义相反，直接透传会跳到章尾。

**⚠️ 头部用 `Stack` 让 Tab 真正居中**

若用 `Row`，返回按钮会占掉左侧宽度、把 Tab 组挤偏；想在 `Row` 里补正就得写一个
"与返回按钮等宽"的魔法数字，而那个宽度随字号/字体变化，迟早对不上。
`Stack` 下层放铺满整宽的居中 Tab 组、上层贴左放返回按钮，没有这个问题。

**⚠️ `onPageHide` 要停表**

阅读页 push 到目录页时**不触发** `aboutToDisappear`（页面还在栈里，状态保留），
所以不能在那里 dispose。但必须调 `vm.onBackground()`（内部 `flush(true)`）：
`ProgressService` 按"上次结算时刻 → 现在"累计时长，离开时不停表，
用户在目录页停留的几分钟会被算进**阅读时长**。

### 5.5.2 书签（长按选中 → 弹窗）

**入口**：**长按正文选中文字** → 系统菜单里的「书签」（在「复制」左边，排第一位）。
**填写**：点「书签」弹出 `BookmarkDialog`，三块内容 ——
① 第几章（只读）② 选中的内容（只读）③ 备注（可输入）→ 取消 / 保存。
**查看/删除**：目录页的「书签」Tab。

> ⚠️ **入口曾经在顶栏，已按反馈移除**。用户的心智是"选中一段 → 对这段做点什么
> （复制 / 书签）"，与系统复制同一个入口最自然；顶栏那个独立按钮既占位置，
> 又和"选中"这个动作脱节。

**实现**：`Text.editMenuOptions()`（`EditMenuOptions`）——
`onCreateMenu` 往系统菜单里加自定义项，
`onMenuItemClick` 用 `TextMenuItemId.equals()` 认领自己的项并返回 `true` 消费事件，
其余项返回 `false` 交回系统。

> ⚠️ 自定义项要放在**首位**（`[自定义项].concat(menuItems)`），
> 追加到末尾会被系统折进 `∨` 展开箭头里 —— 用户实测"看不到书签"。
>
> ⚠️ `editMenuOptions` 收的是 `EditMenuOptions` **数据**，不是 `@Builder` ——
> 别顺手写成 UI 构建器。
>
> ⚠️ 对象字面量先赋给**带类型注解的局部变量**再返回，
> 满足 ArkTS `arkts-no-untyped-obj-literals`。

> ⚠️ 自定义项要放在**首位**（`[自定义项].concat(menuItems)`），
> 追加到末尾会被系统折进 `∨` 展开箭头里 —— 用户实测"看不到书签"。
>
> ⚠️ **用白名单保留，但务必逐项确认要留哪些**：系统默认给的翻译 / 分享 /
> AI 写作等项与本 App 无关（会跳到别的应用或弹系统面板），用户明确要求去掉翻译。
> 但**搜索要保留**（`SEARCH`）—— 本项目没有自己的搜索页，搜索由系统提供，
> 用来查选中的词很实用。
> 白名单的好处是系统**将来新增**的项默认不会冒出来，行为可控；
> 代价是加白名单时必须逐项过一遍，否则会像本项目一样**误删掉搜索**
> （用户实测反馈"搜索功能丢了"，见 pitfall 68）。

**⚠️ 选中态的三件套：点任何一项都要"彻底清选择"**

系统选择菜单与选区状态纠缠得很紧，落地时踩了三个坑，最终收敛成**一个统一入口**
`ReaderPage.clearSelection()` —— 它一次做全三件事：

| 动作 | 不做会怎样 |
|---|---|
| `textController.closeSelectionMenu()` | 菜单不消失（pitfall 70） |
| `hasSelection = false` | 后续点击会被误判成"取消选择" |
| **`selStart/selEnd = 0`** | **重绘把选区复活 ⇒ 系统菜单重新弹出、挡住弹窗**（pitfall 73） |

> ⚠️ 第三项最隐蔽：正文 `Text` 绑着 `.selection(selStart, selEnd)`，
> 而 `selection` 是**构建期属性** —— 只要不清端点，弹窗一打开触发重绘，
> 它就把旧选区重新施加回去。**加延迟完全没用**（只是把复活推迟了）。
> 修法是"点任何一项，第一件事就 `clearSelection()`"。
>
> **判据：凡是"用属性回填系统组件状态"的写法，取消时也必须回填"空状态"，
> 否则任何重绘都会把它复活。**

> ⚠️ `TextController` **只有** `closeSelectionMenu()`，没有"清除选中高亮"的方法
> （SDK 里也没有 `TextSelectionManager`）。清除高亮只能靠 `selection(0, 0)`
> ——文档明确 `start >= end` 即"不选中任何文字"。

**⚠️ 滚动模式的单击要按"按住时长"区分点击与长按**

滚动模式的单击挂在 `parallelGesture(TapGesture)` 上，它的语义是
"**可与子节点手势同时触发**" ⇒ 长按选中正文后松手时它也触发，
`handleReaderTap` 看到有选中就去关菜单，表现是**菜单一闪就消失**（pitfall 74）。

解法：`onTouch` 在 `TouchType.Down` 记录时刻，`handleReaderTap` 开头判断
"超过 `AppConstants.READER_TAP_MAX_MS`(400ms) 就放行不处理"。

**⚠️ 弹窗是"屏幕居中的卡片"，不是从底部升起的抽屉**

用户明确要求居中样式。实现：页面内 `Stack` 全屏遮罩 + `alignContent(Alignment.Center)`
居中的卡片（宽 88%、四角圆、`constraintSize({maxHeight:'80%'})` 防顶出屏幕）。

> 居中还有个附带好处：**不贴底就不必为手势条留安全区**，
> 因此 `BookmarkDialog` 不需要 `safeAreaBottom` 属性
> （对比 `SettingsPanel` / `ReaderBottomBar` 那些贴底浮层就必须有）。

**⚠️ 弹窗用页面内浮层，不用 `@CustomDialog`**

本项目已有成熟的浮层范式（`SettingsPanel` / 目录页遮罩层），都是
"页面内 `if` 条件渲染 + 遮罩 + `ReaderTheme` 配色"。
`@CustomDialog` 要走独立的 `CustomDialogController`、主题色还得另传一遍 ——
没必要为一个弹窗引入第二套机制。

弹窗是**第 5 层（最顶）**：它由长按触发，可能发生在菜单已弹出时，
必须保证盖在设置面板/菜单之上。

> ⚠️ `@Prop draft` 配 `@Watch` 重置输入框：ArkUI 可能**复用**组件实例
> （`bookmarkVisible` 反复开关时），只在 `aboutToAppear` 初始化会让第二次打开
> **残留上一次的备注**。`@Watch` 要挂在被观察的属性（`draft`）上，
> 不是挂在 `note` 上 —— 挂在 `note` 只会在用户打字时回调。

**⚠️ 保存时"同位置已有书签"要软删再新增，不能只更新备注**

只 `updateNote` 会漏掉"选文变了"的情况（用户在同一起点重新选了另一段），
库里留着旧的 `selected_text`，与用户刚确认的内容不一致。
软删 + 新增保证存下来的**就是**用户确认的那一份，且旧行已标记删除、列表不会出现两条。

**⚠️ 开 `copyOption` 后，父节点的 `onClick` 会失效（"点中间打不开状态栏"的根因）**

给正文 `Text` 开了 `copyOption`（可长按选中）之后，它作为子节点会参与触摸竞争，
把单击**吃掉** —— 挂在祖先 `Scroll` 上的 `onClick` 再也收不到，
表现就是"点屏幕中间打不开状态栏"（用户实测反馈）。

解法：祖先的单击改用 `parallelGesture(TapGesture)`（语义：与子节点手势**并行**识别），
而不是 `onClick`。正文照旧长按选中，父节点也能收到单击。

> **判据：一个可选中/可拖拽的子节点，会改变祖先 `onClick` 的命中结果 ——
> 祖先要用 `parallelGesture` / `priorityGesture` 显式表态，不能默认 `onClick` 还能收到。**

**⚠️ 菜单点完不会自己消失，必须显式关掉**

系统选择菜单在点了任一项后**不会自动收起**（用户实测：菜单一直悬在正文上挡着阅读，
全选后尤其顽固，"必须返回页面才能消除"）。
解法：`onMenuItemClick` 里**第一件事**就是 `textController.closeSelectionMenu()` ——
`TextController` 上唯一的关闭入口（所以 `Text` 要用 `Text(content, { controller })` 拿到它）。

**⚠️ "复制"要自己写剪贴板，不能交给系统默认行为**

实测走系统默认"复制"时内容**没有真正进入剪贴板**（用户反馈"复制了之后没有到剪切板中"）。
既然这次点击已被我们拦下（`onMenuItemClick` 返回 `true`），就顺手用
`pasteboard.getSystemPasteboard().setDataSync(...)` 把剪贴板写对。

> ⚠️ 复制的是**原文**内容（先 `toOriginalOffset` 换算再 `originalTextBetween` 截取）：
> 直接从 `renderedText` 截会带上装饰插入的全角缩进空格。

**⚠️ 选中文字后点别处，必须"只取消选择"，不能顺手翻页**

用户实测：左右翻页模式下，选中文字后点外面想取消，结果**直接翻了一页**，选择状态还留着。

**不用"透明蒙层"实现**（虽然直觉上最直接），因为蒙层铺满全屏后会与**选择手柄**打架：

| 蒙层 hit test | 后果 |
|---|---|
| `HitTestMode.Default` | 连**选择手柄的拖动**一起挡掉 → 用户没法调整选区 |
| `HitTestMode.Transparent` | 点击照样传到下层 → 等于没拦 |

改用**在点击处理里判断**（`handleReaderTap`）：有选中时，第一次点击只
`closeSelectionMenu()` + 清标记然后 `return`，不翻页也不切菜单。
效果与"点外面就关掉"完全一致，但**不碰触摸层级**，手柄照常可用。

> ⚠️ 分页模式的三个分区与滚动模式的 `parallelGesture(TapGesture)` **都要**走这个统一入口，
> 漏掉任何一处都会留下"某个模式下点外面仍然翻页"的缺口。

**⚠️ 分页模式下"翻页层"与"正文长按选中"存在触摸竞争**

分页模式第 2 层（翻页层）铺满全屏且绑了 `onClick`，而 ArkUI 默认的
`HitTestMode.Default` 是"自身响应 + **阻塞被遮住的兄弟节点**" ——
下层正文收不到长按、选不中文字。

解法：给该层 `.hitTestBehavior(HitTestMode.Transparent)`
（自身与子节点照常响应，**同时允许**被遮住的节点参与命中）。

> 它带来的"选中后点别处会顺带翻页"由 `handleReaderTap` 解决（见上），
> **不要**靠继续调 hit test 去打补丁 —— 那会把选择手柄的拖动一起弄坏。

**⚠️ 选中回调给的是"渲染文本下标"，书签必须存"原文偏移"**

`TextRange.start` 是相对 `renderedText` 的，而渲染前做过两步装饰
（剥页首换行 + 给段首补 `firstLineIndent` 个全角空格）。
书签与进度一律以**原文偏移**为准（§5.1 铁律），直接存渲染下标会让书签落到错误位置，
**缩进越多偏得越远**。换算入口：`ReaderViewModel.toOriginalOffset()`。

> ⚠️ 换算**不要**重建一遍缩进判断 —— 那等于把 `indentParagraphHeads` 抄第二份，
> 将来改一处忘另一处就会**静默**错位（本项目已在"测量与渲染不同源"上踩过，见 pitfall 57/59）。
> 改用**双游标对齐**：`state.renderedText` 本身就是装饰后的唯一真相，
> 拿它和原文片段逐字符对齐即可，天然与装饰实现同步。
>
> 原理：装饰只**插入**字符、从不删除或改写原文，所以两游标错位时
> 一定是渲染侧多了一个插入字符，只推渲染游标即可。
> 且"行首已带空白就不插入"这条规则保证插入的空白**不会**与原文该位置字符相同，
> 因此不会误判。

**⚠️ 保存结果要区分"新建"与"覆盖"，且与"失败"分开**

保存成功有两个**用户需要区分**的结局：新建了一条 / 覆盖了同位置已有的那条。
用 boolean 只能表达成功/失败，弹窗就没法给准确反馈（用户会疑惑"我刚才是加了一条还是改了一条"）。
所以返回 `BookmarkSaveResult { ok, updated }`，页面给三种文案
（已添加 / 已更新该书签 / 保存失败）。

> ⚠️ **失败必须与成功态分开**：若失败和某个成功态共用返回值，
> 页面就会在失败时提示成功（本项目踩过，见 pitfall 63）。

**交互**
- ✅ 单击左 1/3 上一页、右 1/3 下一页、中间呼出/隐藏菜单（分页模式）
- ✅ 左右滑动翻页（分页模式，`PanGesture` 取 `offsetX` 判正负；scroll 模式滑动即滚动正文）
- ✅ 章节标题 = 正文第一行：字号 = 正文 + `AppTheme.SIZE_STEP`、加粗、左右不留边距（要与正文对齐）。
  只在每章开头出现，**不常驻**
- ✅ 章末自动衔接下一章：page 模式翻到末页自动进入下一章；scroll 模式滚到章末**静默**加载下一章并滚回顶部（见下）
- ✅ 滚动模式：整章可滚 + `onScroll` 节流上报偏移
- ✅ 顶部栏：返回 + 章节名 + 目录入口
- ✅ **常驻底栏**（永远可见，两种翻页模式都有）：左=当前章节名，
  右=`页码 百分比`（如 `5/16  97.1%`；scroll 模式无页码，只显示百分比）。
  上方一条分隔线与正文隔开。章节名只在换章时变，页码/百分比随翻页更新。
  字号用 `AppTheme.FONT_CAPTION`，整条高度 `AppTheme.READER_FOOTER_HEIGHT`
- ✅ 菜单底栏（点中间才出现，**只放操作**）：设置 + 进度条 + 上一章/下一章。

- ✅ 目录页（**独立页面**，不是抽屉）：目录 / 书签两个 Tab，左上角返回；
  目录列表带当前章高亮 + 打开时自动滚到当前章；书签可跳转、可删除（见 §5.5.1、§5.5.2）
- ✅ 阅读设置面板（字号 / 行距 / 段间距 / 首行缩进 / **字间距** / **页边距** / 翻页方式 / 四套背景）：
  入口在底栏第一行右侧，**就地生效**，没有"确定/取消"（见下）
- ✅ 加书签：**长按选中正文** → 菜单里「书签」（在「复制」左边）→ 弹窗填备注后保存
- ⏳ 音量键翻页
- ⏳ 长按选文、划线、笔记

> **为什么设置面板是"就地生效"而不是"改完点确定"**
> 调字号、行距这类参数，用户要的是**看着正文调** ——
> 改完再点确定，等于让他盲调。所以每动一下就回调 `onChange` 立刻重排。
> 代价是每次改动都要清分页缓存 + 重排，所以滑块类一律**松手才提交**
> （`SliderChangeMode.End`），字号则用离散档位而不是连续滑块。

> **⚠️ 切换翻页方式必须重载整章，不能只重算分页**
> `page` 模式下 `renderedText` 只是当前那一页的文本；
> 切到 `scroll` 却只 `buildPagination + renderAt` 的话，
> 正文区只会显示一页内容 —— 表现是"切到滚动模式后整章没了"。
> `ReaderViewModel.updateSettings()` 因此比对 `pageMode` 是否变化，
> 变了就走 `loadChapter`（并借 `restoreToOffset` 把位置带回当前偏移而不是章首）。

> **为什么"读到第几章"必须放在底栏，而不是做成常驻页眉**
> 常驻页眉会永久吃掉正文一行（分页高度处处不同），
> 而底栏本来就只在菜单弹出时出现 —— 把常驻信息放进去，正文一行不占。
> 页眉那条路第一版做过，被否掉了：用户要的是"章节标题出现在每章开头"，不是每页重复一遍。

**⚠️ 首页给章节标题让位：分页服务必须知道这件事**

分页按"整屏容量"装箱，而本章**第一页**顶端多了一行标题 ⇒ 不扣除就会多算一行，
第一页最后一行被裁掉（裁掉的还是正文，用户根本看不出原因）。
所以 `computeBreaks` 多了一个 `firstPageExtraHeight`，`buildLayoutKey` **也必须带上它** ——
同一个容器尺寸下"首页有标题"与"首页无标题"是两组不同断点，共用 key 会互相覆盖。

配套的第二个坑：**分页要量的是高度恒定的容器，不能量正文 Text**。
page 模式下正文 Text 在首页要给标题让位（矮一截），翻到第二页又变回来 ⇒
`onAreaChange` 触发重新分页 ⇒ 页码归零 ⇒ 又回首页 ⇒ **死循环**。
所以量的是第 1 层那个高度恒定的 `Column`，标题高度单独传给分页服务。

**⚠️ 章末自动衔接的三个约束（每一个漏掉都会变成一个可见 bug）**

1. **必须静默加载**（`ReaderViewModel.continueToNextChapter()` → `switchChapter(..., silent=true)`）。
   普通切章会置 `loading=true`，正文区先变成转圈的占位符再换内容 ——
   那一下"正文消失"正是"不能无缝衔接"的观感来源。
2. **必须先判断"这一章到底能不能滚"**（`scrollContentHeight > viewportHeight`，量的是"标题+正文"的内容总高度）。
   章节短到一屏放得下时，滚动条本来就在底部，每来一次滚动回调都会判定"到底了" ⇒
   **短章无限自动连跳**直到全书末尾。这是本功能最容易踩的坑；
   量错成"只算正文不含标题"则会在离章末还差一行时提前衔接。
3. **必须有冷却时间**（`AUTO_CONTINUE_COOLDOWN_MS`）。
   切章过程中还会到达若干次滚动回调，此时"到底了没"用的仍是旧内容的高度，不冷却就会连跳好几章。
   另外切换后要 `scrollEdge(Edge.Top)`：内容换了但滚动位置还停在旧的 max 处，
   新章会从**末尾**开始显示。

**三个关键设计**

| 决定 | 理由 |
|---|---|
| **进度只存「章节序号 + 章内偏移 + 百分比」** | 页码不是稳定量：字号、行距、边距、屏幕宽度任一变化，页边界全变。存页码 = 换字号必丢进度 |
| **断点缓存按 `layoutKey` 区分** | `layoutKey` 由排版参数 + 正文区尺寸拼成可读字符串（`w360_h640_fs18_lh1.6_...`）。用可读串而非哈希：出问题能直接在库里看出这条缓存是什么排版参数 |
| **"待恢复偏移"字段** | 分页依赖正文区**实际尺寸**，而尺寸要等首帧布局后才知道。流程是 open()（恢复进度）→ 拿到尺寸 → 重算分页 → 重载本章，而重载会把 offset 归零 ⇒ 必须有字段记住"要恢复到哪" |

**⚠️ `@Prop` 不是可选项：普通成员只在组件创建时取一次快照**

底部进度栏第一版用普通成员接收 `percent`，结果**拖动进度条后数字又弹回去** ——
父组件状态变了，但子组件里那个字段还是创建时的旧值。
`ReaderTopBar.title` / `ReaderBottomBar` 的各个展示值
（`percent` / `chapterTitle` / `pageText` / `hasPrev` / `hasNext`）全部必须是 `@Prop`。

**判据：凡是"父组件状态变了、子组件要跟着变"的展示值，一律 `@Prop`，不要用普通成员。**

**技术点**
- `ChapterReadService` 按字节偏移随机读 + 内存 LRU（**按字符数限额**，不是按条数）
- `PaginationService` 用"估算行容量"装箱出断点，断点是**章内 UTF-16 下标**
- 进度落库：内存态 + 10 秒节流 / 切后台 / 退出阅读页时强制 flush
- 阅读时长：空闲超过 5 分钟暂停计时，单次结算截断 15 分钟（防进程被杀后残留时间戳）

- **写入时快照**：表结构补 `book_title` 列（`StatsCol.BOOK_TITLE`）；
  `StatsService.submit(bookId, seconds, bookTitle)` 带上当前书名，
  `ReaderViewModel.close()/onBackground()` 从 `state.book.title` 取值；
- **删除时回填**：`BookRepository.hardDelete()` 在 `DELETE` **之前**先把书名
  写进该书的统计行。这一步覆盖"**快照为空就被删**"的那一批 ——
  例如补列之前写下的统计行，只靠写入时快照永远补不回来。

其余细节：
- upsert 用 `CASE WHEN excluded.book_title <> ''` —— 空串**不覆盖**已有快照，
  于是"改名后继续读"会刷新为新名，拿不到书名时也不会把名字抹掉；
- 回填用 `IFNULL(子查询, book_title)` —— 书不存在时子查询返回 NULL，
  而该列是 `NOT NULL`，不包 `IFNULL` 会抛约束错误、把正常删除变成失败；
- 读取用 `IFNULL(b.title, MAX(s.book_title))`：**书还在架上就用实时书名**
  （改名立刻生效），删了才用快照。`MAX()` 是因为按 `book_id` 分组时
  `book_title` 是非聚合列，SQLite 会**任取组内一行** ——
  早期行可能是空串，`MAX` 取字典序最大者即"组内最完整的那份快照"
  （`IFNULL` 挡不住空串，空串不是 NULL）。

⚠️⚠️ **迁移路径上禁止调用会 `await ensureReady()` 的方法**：

## 4. 数据模型

### 4.1 三条铁律（写代码前必须遵守）

**铁律 1：`chapter_index` 一律 0-based，"无进度"用 `-1`。**
初版设计里 `chapter` 表写"从 1 开始"，而 `book.last_chapter_index` 默认 `0` 表示无进度 ——
于是 `0` 同时是"无进度"和"第一章"，只要有一处用 `chapters[chapter_index]` 取值就整体错位一位。

**铁律 2：偏移量分两种单位，不得混用。**

| 用途 | 单位 | 说明 |
|---|---|---|
| `chapter.start_offset` / `end_offset` | **原文件字节偏移** | 用于 `fs.read(fd, buf, {offset})` 随机读。字节单位才有 seek 能力 |
| `annotation` / `page_cache.breaks` / `ReadingPosition.offset` | **章内 UTF-16 代码单元下标** | 即 ArkTS `string` 的天然索引，与 `Text.onTextSelectionChange` 同源 |

**铁律 3：进度绝不存页码。** 见 P2 的关键设计。

**铁律 4：事务内禁止"写完立刻回查"。**

实测结论（自检页 A/B/C/D 四组对照）：

| 组 | 做法 | 结果 |
|---|---|---|
| A | 事务**外** `executeSql` 插入后回查主键 | ✅ 拿到 id |
| B | 事务**内** 同样写法 | ❌ 回查得 **0**，但提交后该行确实存在 |
| C | 事务**内** typed `store.insert()` | ✅ 直接返回 rowId |
| D | 事务**内** `executeSql` + `last_insert_rowid()` | ❌ 得 **0** |

即：**事务内 `querySql` 读不到同一事务刚写入的数据**（推测是连接池把查询派发到了另一条连接）。
`last_insert_rowid()` 也失效，说明这不是"按某列回查"的问题，而是事务内一切读取都看不到本事务的写入。

因此规定：
1. **需要主键时用 typed 接口**（`store.insert()` / `store.batchInsert()`）—— 它们直接返回 rowId，不查库
2. **事务内只允许"先读后写"**：读取必须发生在写入之前
3. 更新/删除类操作不需要主键，用 `executeSql` 即可
4. 这个坑极具误导性：错误信息是"写入失败"，但真相是"写入成功、读回失败"，
   很容易让人去排查 INSERT 语句或表约束。**排查时先做 A/B 对照（事务内 vs 事务外）**

### 4.2 表结构（6 张）

#### 表 1：`book`（书籍表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| uuid | TEXT | 稳定文件标识，用于沙箱文件名。**唯一索引** |
| title / author | TEXT | 书名 / 作者 |
| cover_path / file_path | TEXT | **沙箱相对路径**，不含 `filesDir` 前缀 |
| format | TEXT | `txt` / `epub`，带 CHECK |
| encoding | TEXT | `utf-8` / `gbk` / `gb18030` / `big5` / `utf-16le` / `utf-16be` |
| file_size / file_hash | INTEGER / TEXT | 字节数 / 原始文件字节的 SHA-256 |
| group_id | INTEGER | 外键 → `book_group.id`，可空 |
| total_chapters / word_count | INTEGER | 解析后汇总 |
| added_at / updated_at / last_read_at | INTEGER | 毫秒时间戳 |
| **last_chapter_index** | INTEGER | **0-based，-1 = 无进度** |
| last_offset | INTEGER | 章内 UTF-16 下标 |
| read_status | INTEGER | 0未读 1在读 2读完 |
| progress_percent | REAL | 0~1，冗余字段便于书架排序 |
| **location** | TEXT | JSON 兼容层，见下 |
| parse_status | INTEGER | 0待解析 1解析中 2成功 3失败 |
| parse_error / parse_rule | TEXT | 失败原因（含"文件丢失"）/ 命中的分章规则 |
| metadata | TEXT | 扩展元数据（EPUB OPF 等） |
| deleted | INTEGER | 软删除 |

**`location` JSON 契约（定死，不留自由发挥）**
```jsonc
{ "type": "txt", "chapterIndex": 12, "offset": 340, "percent": 0.213 }
{ "type": "epub", "href": "OEBPS/ch03.xhtml", "anchor": "p12", "cfi": "/6/4!/4/2", "percent": 0.213 }
```
`last_chapter_index` + `last_offset` 是**权威进度**；`location` 是与格式无关的兼容层，两处必须同源同事务写入。

> **决策记录：`file_path` 为什么存相对路径而不是绝对路径**
> `filesDir` 在应用升级/迁移后会变。存绝对路径的话，升级后所有书记录都指向不存在的文件，
> 表现是"书还在书架上、点开说文件丢失"，而且**不报错、没有异常堆栈**。
> 相对路径 + 运行时拼接是唯一稳妥的做法。

#### 表 2：`chapter`（章节表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| book_id | INTEGER | 外键 → `book.id`，`ON DELETE CASCADE` |
| title | TEXT | 章节标题（**不含换行符**） |
| **start_offset** | INTEGER | **原文件字节偏移，指向标题行之后的正文首字节** |
| **end_offset** | INTEGER | 原文件字节偏移（不含），等于下一章标题行首；末章为 NULL |
| href / anchor | TEXT | EPUB 用 |
| level | INTEGER | 0=章 1=卷 |
| word_count | INTEGER | 估算字数 |
| chapter_index | INTEGER | **0-based**，`UNIQUE(book_id, chapter_index)` |

> **⚠️ `start_offset` 必须指向标题行之后的正文首字节，而不是标题行本身**
>
> 这是实测踩到的坑：若 `start_offset` 取标题行首，第 1 章读出来会变成
> `"第一章 初入江湖\n这是第一章的正文。..."` —— 标题混进了正文。
> 而第 2 章之后恰好正常（因为上一章的 `end_offset` 把标题留在了上一章末尾），
> **所以这个 bug 只在第 1 章暴露，极易漏测**。
>
> 约定：
> - `chapter.title` 单独存标题文本，目录用；
> - `start_offset` = 标题行首字节 + 标题行含换行符的字节长度（`\r\n` 算两个字节）；
> - `end_offset` = 下一章标题行的首字节（因此本章末尾会带一个空行，属正常）；
> - 阅读页因此**不需要**再重复渲染标题。

#### 表 3：`annotation`（书签 / 划线 / 笔记表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| book_id / chapter_id / chapter_index | INTEGER | **`chapter_id` 是外键真相，另两列是查询冗余** |
| start_offset / end_offset | INTEGER | 章内 UTF-16 下标；书签可空（只记章首） |
| selected_text / note_content | TEXT | 选中文本 / 笔记内容 |
| type | INTEGER | 1书签 2划线 3笔记，带 CHECK |
| color | TEXT | 划线颜色 |
| created_at / updated_at / deleted | INTEGER | |

> **决策记录：为什么留 `book_id` / `chapter_index` 两个冗余列**
> 书签列表要按章排序、目录要按章聚合标记，若只留 `chapter_id` 就得每次 JOIN `chapter`。
> 代价是**三处必须一致** —— 所以新增标注时冗余列由 `AnnotationRepository.add()` 统一反查填充，
> **禁止业务层自己拼 INSERT**（三处不一致会让书签在目录里串章，且不报错）。

#### 表 4：`book_group`（分组表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| name | TEXT | 分组名，`UNIQUE WHERE deleted = 0` |
| sort_order | INTEGER | 越小越靠前 |
| created_at / updated_at / deleted | INTEGER | |

> **⚠️ `ON DELETE SET NULL` 在软删除下永远不会触发**
> 删除分组必须在事务里**手动**把成员 `group_id` 置 NULL，
> 否则会出现"书指向一个已删除的分组"而从书架消失。见 `GroupRepository.softDeleteWithMembers()`。

#### 表 5：`reading_daily_stats`（阅读统计表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| book_id | INTEGER | **0 = 全局统计**（哨兵值，不参与外键） |
| date | TEXT | `YYYY-MM-DD`，**本地时区** |
| duration_seconds | INTEGER | 阅读时长（秒） |
| book_title | TEXT | **写入当时的书名快照**（V2 新增），见下 |
| updated_at | INTEGER | |

约束：`UNIQUE(book_id, date)`。

> **⚠️ 写入必须 upsert**：`INSERT ... ON CONFLICT(book_id, date) DO UPDATE SET duration = duration + excluded.duration`，
> 否则同一本书同一天会产生多条记录，"今天读了多久"时对时错。
> **⚠️ 日期用本地时区**：用 UTC 的话，晚上 8 点后的阅读会被算到"明天"，连续打卡天数会对不上。
> **⚠️ `book_title` 为什么存在**（V2 新增）：本表**没有外键**，书被物理删除后统计行会留下，
> 而书名只在 `book` 表 —— 不留快照的话，阅读记录里那本书只能显示「已移除的书」。
> upsert 时用 `CASE WHEN excluded.book_title <> ''` 更新：空串**不覆盖**已有快照，
> 于是"改名后继续读"会刷新为新名，而拿不到书名的调用不会把名字抹掉。
> 读取用 `IFNULL(b.title, s.book_title)`：**书还在架上就用实时书名**，删了才用快照。

#### 表 6：`page_cache`（分页缓存表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| book_id / chapter_index | INTEGER | |
| layout_key | TEXT | 排版方案指纹，见下 |
| breaks | TEXT | 断点数组 JSON，元素为**章内 UTF-16 下标** |
| page_count | INTEGER | 冗余，便于快速显示 |
| updated_at | INTEGER | |

约束：`UNIQUE(book_id, chapter_index, layout_key)`。这是**纯派生数据**，可直接清空，不需要 `deleted` 列。

**`layout_key` 的计算口径（必须定死）**
```
w{内容宽}_h{内容高}_fs{字号}_lh{行距}_ps{段距}_ls{字距}_fi{首行缩进}_ff{字体}
```
用**可读字符串**而非哈希：单条缓存几百字节，存储压力可忽略；出问题时能直接在库里看出排版参数。

> **⚠️ 不要用 delta 编码存断点**
> `breaks` 与正文一一对应，保留**绝对值**。delta 方案下一处损坏会导致整章错位，
> 而绝对值最坏只是某一页不准。约定 `breaks[0] === 0`，第 i 页覆盖 `[breaks[i], breaks[i+1])`。

### 4.3 索引（15 条）

```sql
-- 书籍
CREATE UNIQUE INDEX uq_book_uuid ON book(uuid);
CREATE UNIQUE INDEX uq_book_hash ON book(file_hash) WHERE deleted = 0 AND file_hash <> '';
CREATE INDEX idx_book_shelf  ON book(deleted, last_read_at DESC);
CREATE INDEX idx_book_group  ON book(group_id, deleted);
CREATE INDEX idx_book_status ON book(deleted, read_status, last_read_at DESC);

-- 章节（UNIQUE(book_id, chapter_index) 已生成隐式索引，不再重复建）
CREATE INDEX idx_chapter_title ON chapter(book_id, title);

-- 标注
CREATE INDEX idx_annotation_book    ON annotation(book_id, chapter_index, deleted);
CREATE INDEX idx_annotation_chapter ON annotation(chapter_id, deleted);
CREATE INDEX idx_annotation_type    ON annotation(book_id, type, deleted);

-- 分组
CREATE UNIQUE INDEX uq_group_name ON book_group(name) WHERE deleted = 0;
CREATE INDEX idx_group_sort ON book_group(deleted, sort_order, id);

-- 统计（UNIQUE(book_id, date) 已覆盖 book_id 前缀查询）
CREATE UNIQUE INDEX uq_stats_book_date ON reading_daily_stats(book_id, date);
CREATE INDEX idx_stats_date ON reading_daily_stats(date);

-- 分页缓存
CREATE UNIQUE INDEX uq_page_cache ON page_cache(book_id, chapter_index, layout_key);
CREATE INDEX idx_page_cache_book ON page_cache(book_id);
```

> **⚠️ 两条索引刻意不建**（它们与各自的 UNIQUE 约束完全重复，只会拖慢批量导入）：
> `idx_chapter_book(book_id, chapter_index)` 与 `idx_stats_book(book_id, date)`。

> **⚠️ `idx_book_shelf` 为什么不是单列 `last_read_at DESC`**
> 书架查询**一定**带 `deleted = 0`。单列索引在这种查询下会被放弃（选择性差），
> 复合索引把主查询列放最前才有效。

### 4.4 写入路径（已定案）

| 操作 | 路径 | 原因 |
|---|---|---|
| 导入入库 | **单事务**：`insert(book)` → `batchInsert(chapter, 每 500 条)` → `updateParseState` | 要么全成要么全不成，避免"书在架但一章都没有"的僵尸记录 |
| 取新书主键 | `store.insert()` 的返回值 | 铁律 4 |
| 阅读进度 | 内存态 → 10 秒节流 / 切后台 / 退页时 `UPDATE book SET last_chapter_index, last_offset, location, progress_percent, last_read_at` | 不每页写库 |
| 阅读时长 | 事务内 upsert 两条：`book_id = 本书` 和 `book_id = 0`（全局） | 统计页与书籍详情各取所需 |
| 删除分组 | 事务内：先 `UPDATE book SET group_id = NULL`，再软删分组 | `ON DELETE SET NULL` 在软删除下不触发 |
| 软删除书籍 | `UPDATE book SET deleted = 1`，**沙箱文件保留** | 便于恢复 |
| 硬删除书籍 | `DELETE FROM book`，`chapter`/`annotation`/`page_cache` 由外键 CASCADE 带走 | 依赖外键真正生效（见 §5.6 第 6 条） |

### 4.5 版本迁移（两条独立机制）

| 机制 | 作用域 | 用途 |
|---|---|---|
| `DbConstants.SCHEMA_BUILD` | **开发期** | 编进库文件名（`novel_reader_b2.db`）。改 DDL 就 +1，等于换一个全新的库文件 |
| `DbConstants.DB_VERSION` + `RdbHelper.migrate()` | **发布后** | 在同一个库文件内按版本号补列/补表/补索引，保留用户数据 |

> **⚠️ 为什么必须有 `SCHEMA_BUILD`（实测踩坑）**
> `CREATE TABLE IF NOT EXISTS` **永远不会修改已存在的表**。
> 开发过程中一旦改过 DDL（例如给 `format` 补 `DEFAULT 'txt'`），设备上残留的旧库就与新代码不一致。
> 典型症状：插入时报 `SQLite: Abort due to constraint violation` ——
> 因为旧表没有 `format` 的默认值，省略该列时它成了 NULL，撞上 NOT NULL 或 CHECK。
> 这个错误极具误导性：看起来像代码写错了，实际上是表结构过期。
>
> **排查耗时一整轮，所以定成规矩：开发期改任何 DDL，必须把 `SCHEMA_BUILD` +1。**

**迁移规则**
1. `migrate()` 里每一步必须**幂等**，用户可能在迁移中途被杀进程
2. **只允许加列 / 加表 / 加索引**。SQLite 不支持改列类型或删列，
   真要改必须走"建新表 → 拷数据 → 换名"，属发布级破坏性变更，需单独评估
3. `RdbHelper.addColumnIfMissing()` / `hasColumn()` 已提供，直接复用

### 4.6 偏好设置（Preferences）

使用单个实例 `reader_settings`，全部 key 集中在 `SettingsKeys` 常量类中。

| 分类 | key |
|---|---|
| 元信息 | `schema_version`、`first_launch_done` |
| 排版 | `font_size` `font_family` `line_height` `paragraph_spacing` `page_margin` `letter_spacing` `first_line_indent` |
| 显示 | `page_mode` `theme` `bg_color` `keep_screen_on` `hide_status_bar` `volume_key_page` `brightness` |
| 书架 | `grid_mode` `book_sort` |
| TTS | `tts_speed` `tts_voice` `tts_timer_minutes` |

**三条约定**
1. **每个 getter 带默认值**（key 缺失时返回默认值），因此"漏写默认值"不会导致类型错误，首次启动也不需要批量初始化全部 key
2. **写设置逐项 `put` 而不是先 `clear()`**：`clear` 中途失败会把用户所有设置清空，逐项覆盖是幂等的
3. **写设置必须 `flush`**，否则只在进程被杀时暴露，开发期几乎看不出来

> **决策记录：为什么判据是"SQLite 存要查询/聚合/建索引的实体，Preferences 存永远只有一个值的单例配置"**
> 反过来（把设置做成表的行）会让每次读设置都过一次数据库；
> 而把书籍列表塞进 Preferences 则会失去索引与聚合能力。
> 另外**禁止**把单书设置写成动态 key（`book_3_fontsize`）—— 那会无限增长。

data/database/            只有 Repository 能 import
      ↓
model/  common/           纯数据与工具，谁都能用，自身不依赖任何人
```

**三条硬约束**
1. **View 不写业务逻辑**，也不出现 `relationalStore` / `fs` / `preferences`
2. **Repository 只返回 model 对象或状态码，绝不返回 `ResultSet`**
3. **ViewModel 不持有 UI 组件**；`Context` 由 `EntryAbility` 启动时注入，不在各处 `getContext()`

### 5.3 状态管理（ArkUI V1）

本项目用 **V1 观测体系**（`@State` / `@Prop` / `@ObjectLink` / `@Observed`）。

> **决策记录：为什么不用 V2（`@Local` / `@Param` / `@ObservedV2` / `@Trace`）**
> V2 的细粒度刷新确实更好，但参考项目实测出一个 V2 的关键限制（§5.6 第 37 条）：
> `@ComponentV2` 在 SDK 声明里**没有 `@form` 标记**，因此**服务卡片只能用 V1 写**。
> 本项目 P2 阶段要做「继续阅读」服务卡片，如果 App 侧全量上 V2，
> 就会出现"卡片 V1 + App V2"两套心智模型，且 `views/` 下的组件**一个都不能在卡片里复用**。
> 当前代码已按 V1 落地且自检通过，**故保持 V1**。
> 若后续放弃服务卡片，可整体迁移到 V2（迁移项见 §6）。

| 场景 | 本项目用法 |
|---|---|
| 页面内状态 | `@State` |
| 父子传值（需要跟随更新） | **`@Prop`** |
| 数据类深度观测 | `@Observed` + `@ObjectLink` |
| 跨页面版本号 | `AppStorage`（仅作诊断，刷新由根页面驱动） |

**三条硬约束**
1. **`@Prop` 不是可选项**：普通成员只在组件创建时取一次快照，
   父组件状态变了子组件不会更新（实测：进度条数字弹回去）。见 P2
2. **`@Observed` 对象的字段变化要能被观察到**：接收方必须用 `@ObjectLink`，
   普通 `@State` 只在顶层赋值时重绘
3. **同一个组件内部 V1/V2 不能混用**（SDK 限制，混用直接编译失败）

**一条工程习惯**：`@State` 只给**在 `build()` 里被读到的**变量用。
只在方法里用、不参与渲染的字段声明成普通 `private` 成员 —— 否则每次改它都会触发一次无意义的 `build()` 重跑。

### 5.4 状态刷新的正确姿势

**这是本项目踩坑最多的地方，单独成节。**

| 我依赖过的机制 | 是否可靠 | 原因 |
|---|---|---|
| 子页面 `onPageShow` | ❌ | **只对 `@Entry` 页面触发**，普通 `@Component` 拿不到 |
| `AppStorage` 版本号 + `setInterval` 轮询 | ❌ | 定时器在 `aboutToDisappear` 里被清掉，而 Tab 切换**不保证重新 `aboutToAppear`** → 定时器一死就再也没刷新过 |
| `AppStorage.link().onChange` | ❌ | `SubscribedAbstractProperty` **没有 `onChange` 属性**（想当然了） |
| **根页面 `onPageShow` + Tabs `onChange`** | ✅ | 只有 `@Entry` 页面拿得到，且覆盖"从阅读页返回"与"切回 Tab"两个场景 |
| **`TabContent.onWillShow`**（推荐迁移） | ✅ | `@since 12`，声明明确覆盖 first-time display / tab switching / page switching / 前后台切换，覆盖面最全 |

**当前实现（已通过自检）**：根页面驱动 + `ShelfRefreshRegistry`。
**迁移项**：改用 `TabContent.onWillShow`，按 Tab 各持一个 `reloadTick` 计数器（避免一个 Tab 刷新连带另一个白查库）。

### 5.5 存储底座初始化

**问题**：`PathUtil` / `RdbHelper` / `SettingsService` 都需要 Context，而 ViewModel 里拿不到 Context。
**又**：`SettingsService` 的 getter 是**同步**的，`store` 为 null 时会抛错。

**方案：可自愈的幂等初始化**

```
EntryAbility.onCreate
  └── StorageBootstrap.bootstrap(context)   注入 Context，启动初始化（不阻塞窗口创建）
        ├── PathUtil.init(ctx)
        ├── RdbHelper.init(ctx)
        └── SettingsService.init(ctx)

每个服务自己持有 ensureReady()（幂等，缓存 Promise）
  - RdbHelper.ensureReady()      在 queryNumber / query / queryFirst / withTransaction 内部自动调用
  - SettingsService.ensureReady()
```

**页面侧必须显式门控**（这是实测踩到的坑）：

```ts
aboutToAppear(): void {
  this.vm.bind(this.state);
  // 必须先等存储就绪，再让 ViewModel 读设置
  StorageBootstrap.ensureReady().then(() => {
    this.vm.init();
  }).catch((e: Object) => {
    this.state.error = `初始化失败：${Logger.errText(e)}`;
  });
}
```

> **⚠️ 直接调 `this.vm.init()` 会抛 "SettingsService 尚未初始化"**
> `vm.init()` 一进来就要读 `gridMode` / `bookSort`，而 `SettingsService.init()` 还没跑完。
> **依赖顺序的地方，要让调用结构保证顺序，而不是靠"我记得先调这个"。**

### 5.6 ArkTS 编译器踩坑实录（持续累积）

> 这一节只记录**编译器或真机亲自教过的**规则 —— 每条都有报错编号、`.d.ts` 出处或实测现象。
> 这是本项目真正的资产：这些规则不查就一定会踩，踩一次改一片。

| # | 规则 | 证据 | 正确写法 |
|---|---|---|---|
| 1 | **`util` 没有 `StringEncoder`；`TextEncoder` 只做 UTF-8** | `@ohos.util.d.ts:824` 的 `readonly encoding = 'utf-8'`；全文只有 `TextDecoder` / `TextEncoder` / `StringDecoder` 三个类 | 编码字节长度**按规则直接数**（`ByteLength`），不要用编码器反推。用 `TextEncoder` 算 GB18030 文本会让汉字算成 3 字节（实际 2 字节），字节游标越走越偏 |

| 69 | **`@Prop` 传普通 class 时，子组件的 `@State` 只在首次创建初始化，组件复用会残留旧值** | 弹窗靠 `bookmarkVisible` 反复开关，ArkUI 可能**复用**组件实例 ⇒ 第二次打开时备注框里是**上一次**输入的内容 | 给被观察属性挂 `@Watch` 并在回调里重置本地 `@State`：`@Prop @Watch('onDraftChanged') draft`。⚠️ `@Watch` 必须挂在**被观察的属性**上，挂在 `note` 上只会在用户打字时回调、起不到重置作用 |
| 70 | **系统选择菜单点完不会自己消失** | 用户实测："菜单一直悬在正文上，全选后尤其顽固，**必须返回页面才能消除**" | `onMenuItemClick` 里第一件事就 `textController.closeSelectionMenu()`（`TextController` 上唯一的关闭入口，所以 `Text` 要用 `Text(content, {controller})` 拿到它） |
| 71 | **走系统默认"复制"时内容没进剪贴板** | 用户实测"复制了之后没有到剪切板中"。系统菜单项在我们返回 `true` 时已不再执行默认行为，内容自然没被写入 | 自己写剪贴板：`pasteboard.getSystemPasteboard().setDataSync(pasteboard.createData(MIMETYPE_TEXT_PLAIN, text))`。⚠️ 写剪贴板**不需要**权限（只有读才要 `READ_PASTEBOARD`）；复制内容取**原文**，别从 `renderedText` 截（会带上装饰插入的全角空格） |
| 72 | **"点外面取消选择"用透明蒙层会与选择手柄打架** | 直觉方案是铺一层全屏透明蒙层拦点击，但：用 `HitTestMode.Default` 会**连选择手柄的拖动一起挡掉**（用户没法调整选区）；用 `Transparent` 则点击照样传到下层、等于没拦 | 改为**在点击处理里判断**（`handleReaderTap`）：有选中时第一次点击只 `closeSelectionMenu()` + 清标记并 `return`。效果相同但**不碰触摸层级**，手柄照常可用。⚠️ 分页三区与滚动模式的 `parallelGesture` **都要**走同一入口，漏一处就留下缺口。**判据：想用"铺一层"解决穿透时，先问它会挡住什么别的东西** |
| 73 | **绑了 `Text.selection()` 后，只清"是否有选中"标记不够 —— 重绘会把选区复活，系统菜单跟着重新弹出** | 用户实测"系统菜单一直挡住书签弹窗"，**加延迟完全没用**（把"复活"推迟了而已）。根因：`onMenuItemClick` 只调了 `closeSelectionMenu()` + 把 `hasSelection` 置假，**漏清 `selStart/selEnd`**；弹窗打开触发重绘时，`selection(旧端点)` 又把选区施加回去 ⇒ 菜单重新出现 | 点任何一项**第一件事**就调统一的 `clearSelection()`，它一次做全三件事：关菜单 + 清标记 + **把端点压成 `(0,0)`**（文档：`start >= end` 即不选中任何文字）。**判据：凡是"用属性回填系统组件状态"的写法，取消时也必须回填"空状态"，否则任何重绘都会把它复活** |
| 74 | **滚动模式长按选中后一松手，菜单就消失** | `parallelGesture(TapGesture)` 的语义是"**可与子节点手势同时触发**" ⇒ 长按松手时它也触发，`handleReaderTap` 看到有选中就去关菜单。用户描述："长按时显示、一松手就消失" | 用**按住时长**区分点击与长按：`onTouch` 在 `TouchType.Down` 记录时刻，`handleReaderTap` 开头判断"超过 `READER_TAP_MAX_MS`(400ms) 就放行不处理"。阈值取系统长按阈值(~500ms)与正常点击(<250ms)之间 |
| 37 | **父子组件传参"名字对不上"是静默失败，且症状和加载慢一模一样** | 本项目实测（P0 严重故障）：`Index` 写 `BookShelfPage({ vm: this.shelfVm })`，而 `BookShelfPage` **只声明了 `state`、没有声明 `vm`** → 多出来的 `vm` 被静默丢弃；子组件自己 `new` 了一份 `ShelfState` + `BookShelfViewModel`，数据全部写进 `vm.state`，UI 却盯着另一个 `this.state`。**结果：数据库查询全部成功，界面永远停在"正在加载书架…"，重装 App 也没用**（因为与数据无关） | ①**UI 读的对象与 ViewModel 写的对象必须是同一个实例**：`@Observed` 状态由 `@Entry` 根页面持有，子页面用 `@ObjectLink` 接收，并在 `aboutToAppear` 首行 `vm.bind(state)`；②同一层里两个组件共用状态时，**要么让它 `@ObjectLink`，要么让 VM 显式 `bind()`，绝不能各自 `new`**；③"永远 loading"类故障先查**状态对象身份**，不要先怀疑 IO 慢 |

### 5.7 主题设计

**核心问题：颜色一旦写死在页面里，深色模式就没法做。**
所以第一步不是配色，而是**语义令牌 + 资源引用**。

#### 5.7.1 三层结构

```
第 1 层  语义令牌     resources/base/element/color.json + resources/dark/element/color.json
                     ↓ 页面只引用 $r('app.color.xxx')，绝不写 hex
第 2 层  组件主题类   common/theme/AppTheme.ets（尺寸/圆角/字号）
                     ↓ 供 ArkUI 属性使用；颜色也在此集中引用资源
第 3 层  阅读页配色   common/theme/ReaderTheme.ets（四套配色，见 5.7.3）
```

> **为什么阅读页配色不走资源令牌**
> 阅读页的配色是**用户选择**的（浅色/羊皮纸/护眼/夜间），不是"跟随系统深浅模式"。
> 用资源令牌的话，系统切深色会和用户选择打架。
> 所以阅读页的 `bg` / `text` / `secondary` / `barBg` 走 `ReaderTheme.of(userChoice)` 返回的**普通 class**，
> 而 App 其余部分（书架、设置、我的）走资源令牌跟随系统。

#### 5.7.5 深色模式的实现要点

1. **目录结构**：`resources/base/element/color.json`（浅色）+ `resources/dark/element/color.json`（深色），
   同名令牌自动切换 —— 这是系统能力，不需要手写判断
2. **必须在 `EntryAbility.onCreate` 里用同步读法设好主题**：
   `Preferences` 的 `getPreferencesSync` + `getSync` 是同步 API（`@ohos.data.preferences.d.ts:451/1113`）。
   走异步的话系统会先按默认主题画一帧 —— 深色模式下就是"黑底应用先闪一下白屏"
3. **自己的枚举和平台枚举数值不同时，转换只允许在一处做**：
   ```
   应用 ThemeMode:           平台 ConfigurationConstant.ColorMode:
     FOLLOW_SYSTEM = 0         COLOR_MODE_NOT_SET = -1
     LIGHT         = 1         COLOR_MODE_DARK    =  0
     DARK          = 2         COLOR_MODE_LIGHT   =  1
   ```
   顺序都不一样。**哪里图省事直接把自己的值传给平台，浅色/深色就会反掉，而且不报错。**
   转换收在 `ThemeApplier.applyThemeMode()` 一处
4. **换主题的顺序是「先应用、再落盘」**：反过来的话，万一 `setColorMode` 失败，
   设置已经存下来了，下次启动才生效 —— 用户看到"点了没反应，重启以后变了"，比直接失败更难理解
5. **⚠️ 本项目的特殊情况**：书架/阅读页已有自己的配色逻辑，
   接入令牌前必须先**清掉页面里的 hex 字面量**。当前 `AppTheme` 里的色值就是 hex 字符串
   （`static readonly PRIMARY: string = '#3B6FE0'`）——**这是待改造项**，
   要改成 `brand: Resource = $r('app.color.brand')` 的形态，否则深色模式不会生效
