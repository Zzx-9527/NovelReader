## 1. 项目定位

### 1.1 一句话定位

**「静读」是一款完全离线、无广告、无需注册的本地小说阅读器 —— 导入自己的 TXT 文件，进度永不丢失。**

### 1.2 目标用户

- 手上存有大量 TXT 小说、习惯用手机长时间阅读的用户
- 受够了阅读 App 的广告、会员墙、强制登录与书架同步的用户
- 对隐私敏感、不愿让"我在读什么"被上传的用户
- 鸿蒙 NEXT 用户（生态内好用的本地阅读器稀缺）

### 1.3 三条产品原则

1. **零联网**：工程内不存在任何网络请求代码，书与进度 100% 留在本机
2. **零注册零广告**：打开即用，没有账号、会员、推荐位
3. **进度绝不丢**：这是阅读器的生命线 —— 换字号、重启、切后台都必须回到原处

### 1.4 差异化设计（避免"又一个套壳阅读器"）

| 差异化点 | 具体做法 |
|---|---|
| 编码自动识别 + 可手动纠正 | TXT 圈子里 GBK/GB18030 极常见，多数阅读器只认 UTF-8。本 App 自动探测，判错时可**一键换编码重解析**而不必重新导入 |
| 大文件不崩 | 全书**不整读入内存**：导入时流式分章只记录字节偏移，阅读时按偏移随机读该章 |
| 进度与排版解耦 | 进度只记「章节序号 + 章内偏移 + 百分比」，**绝不存页码**；换字号后仍回到同一句话 |
| 分页结果可缓存 | 排版参数生成指纹 `layoutKey`，按指纹缓存断点；切回同一章不重算 |
| 数据可迁移 | 书籍与进度可导出备份，用户自己保管 |

## 3. 页面详解

> 状态图例：✅ 已完成 · 🟡 部分完成 · ⏳ 待做 · ❌ 已砍

### P0｜根页面（底部导航）
**状态：✅ 已完成**（`pages/Index.ets`）

**目标**：承载 Tabs，并且**作为唯一可靠的刷新时机来源**

**页面结构**
```
Index (@Entry)
├── Tabs { 书架 / 统计 / 我的 }
└── 书架状态由本页的 BookShelfViewModel 持有
```

**⚠️ 这一页存在的真正理由：`onPageShow` 只对 `@Entry` 页面触发**

书架页是普通 `@Component`，它**拿不到** `onPageShow`。
第一版把"从阅读页返回后刷新进度"挂在书架页的 `onPageShow` 上 —— 那个钩子**从来没被调用过**，
表现是"阅读进度只有重启 App 才同步"。这个 bug 花了两轮才定位。

**结论（已定案）：刷新时机必须由根页面显式驱动**

```ts
// Index（@Entry）—— 只有它拿得到这两个可靠时机
onPageShow(): void {
  ShelfRefreshRegistry.refresh();     // 从阅读页返回 / App 回到前台
}
// Tabs
.onChange((index: number) => {
  if (index === 0) {
    ShelfRefreshRegistry.refresh();   // 切回书架
  }
});
```

书架页在 `aboutToAppear` 里把 ViewModel 注册进 `ShelfRefreshRegistry`，
`aboutToDisappear` 里注销。这是一个**受控的全局引用**，不是事件总线：只有一处使用，随页面销毁即清空。

**为什么不给每个 Tab 内容用 `TabContent.onWillShow`**
参考项目（HabitFlow）用的是它，`@since 12`，覆盖 first-time display / tab switching /
page switching / 前后台切换。本项目**也用它**是更好的方案（覆盖面最全），
但当前实现先用根页面驱动把功能跑通；迁移到 `onWillShow` 是下一轮的重构项（见 §6 风险表）。

| 决定 | 理由 |
|---|---|
| **封面用"书名首字 + 浅色底"占位** | TXT 文件没有封面；`Image` **不接受空字符串路径**（会抛错），所以不做无效分支。接入 EPUB 封面时替换这一处渲染即可 |

### P2｜阅读页（核心页面 ⭐）
**状态：🟡 主体完成**（`pages/ReaderPage.ets` + `views/reader/` + `viewmodels/ReaderViewModel.ets`）

**目标**：正文阅读、翻页、跳章、沉浸式，且**进度永不丢**

**页面结构（Stack 分层，顺序即层级）**
```
第 1 层  正文（最底）        page 模式：只渲染当前页；scroll 模式：整章可滚
第 2 层  翻页层（点击 + 滑动） ← 仅当 !menuVisible 且 pageMode !== 'scroll'
第 3 层  顶栏 / 底栏          ← 仅当 menuVisible，在翻页层之上
第 4 层  目录抽屉 + 遮罩      最顶
```

**⚠️ 第 2 层和第 3 层的顺序是踩坑后改的**
第一版把点击分区**常驻**在 Stack 最上层，结果菜单弹出后它盖在顶栏/底栏之上把点击截走 ——
点中间等于又切换一次，菜单**弹出后无法收回**。
`if` 条件里必须有 `!this.state.menuVisible`，两块区域在任何时刻都只存在一个。

**⚠️ 第 2 层还必须在 scroll 模式下缺席（"阅读页划不动"的根因）**
那三个分区 `Column` 都绑了 `onClick`，按 ArkUI 的触摸测试规则
（`HitTestMode.Default`：自身响应 + **阻塞兄弟节点**），它们会把拖拽事件整个吃掉，
下层 `Scroll` 永远收不到滑动 —— 只有点击生效。
滚动模式下点击改由 `Scroll` 自己接管（单击整屏切菜单，短章节时正文下方空白也能点）。
**判据：任何绑定在 Stack 上层的手势层，都要问一句"它会不会把下层需要的拖拽吃掉"。**

**交互**
- ✅ 单击左 1/3 上一页、右 1/3 下一页、中间呼出/隐藏菜单（分页模式）
- ✅ 左右滑动翻页（分页模式，`PanGesture` 取 `offsetX` 判正负；scroll 模式滑动即滚动正文）
- ✅ 滚动模式：整章可滚 + `onScroll` 节流上报偏移
- ✅ 顶部栏：返回 + 章节名 + 目录入口
- ✅ 底部栏：章节名 + 页码 + 百分比 + 可拖动进度条（跳章）
- ✅ 目录抽屉：章节列表 + 当前章高亮 + 点击跳转
- ⏳ 音量键翻页
- ⏳ 阅读设置面板（字号/行距/主题）
- ⏳ 长按选文、划线、书签

**三个关键设计**

| 决定 | 理由 |
|---|---|
| **进度只存「章节序号 + 章内偏移 + 百分比」** | 页码不是稳定量：字号、行距、边距、屏幕宽度任一变化，页边界全变。存页码 = 换字号必丢进度 |
| **断点缓存按 `layoutKey` 区分** | `layoutKey` 由排版参数 + 正文区尺寸拼成可读字符串（`w360_h640_fs18_lh1.6_...`）。用可读串而非哈希：出问题能直接在库里看出这条缓存是什么排版参数 |
| **"待恢复偏移"字段** | 分页依赖正文区**实际尺寸**，而尺寸要等首帧布局后才知道。流程是 open()（恢复进度）→ 拿到尺寸 → 重算分页 → 重载本章，而重载会把 offset 归零 ⇒ 必须有字段记住"要恢复到哪" |

**⚠️ `@Prop` 不是可选项：普通成员只在组件创建时取一次快照**

底部进度栏第一版用普通成员接收 `percent`，结果**拖动进度条后数字又弹回去** ——
父组件状态变了，但子组件里那个字段还是创建时的旧值。
`ReaderTopBar.title` / `TocDrawer.currentIndex` / `ReaderBottomBar` 的三个值全部必须是 `@Prop`。

**判据：凡是"父组件状态变了、子组件要跟着变"的展示值，一律 `@Prop`，不要用普通成员。**

**技术点**
- `ChapterReadService` 按字节偏移随机读 + 内存 LRU（**按字符数限额**，不是按条数）
- `PaginationService` 用"估算行容量"装箱出断点，断点是**章内 UTF-16 下标**
- 进度落库：内存态 + 10 秒节流 / 切后台 / 退出阅读页时强制 flush
- 阅读时长：空闲超过 5 分钟暂停计时，单次结算截断 15 分钟（防进程被杀后残留时间戳）

## 4. 数据模型

### 4.1 三条铁律（写代码前必须遵守）

**铁律 1：`chapter_index` 一律 0-based，"无进度"用 `-1`。**
初版设计里 `chapter` 表写"从 1 开始"，而 `book.last_chapter_index` 默认 `0` 表示无进度 ——
于是 `0` 同时是"无进度"和"第一章"，只要有一处用 `chapters[chapter_index]` 取值就整体错位一位。

**铁律 2：偏移量分两种单位，不得混用。**

| 用途 | 单位 | 说明 |
|---|---|---|
| `chapter.start_offset` / `end_offset` | **原文件字节偏移** | 用于 `fs.read(fd, buf, {offset})` 随机读。字节单位才有 seek 能力 |
| `annotation` / `page_cache.breaks` / `ReadingPosition.offset` | **章内 UTF-16 代码单元下标** | 即 ArkTS `string` 的天然索引，与 `Text.onTextSelectionChange` 同源 |

**铁律 3：进度绝不存页码。** 见 P2 的关键设计。

**铁律 4：事务内禁止"写完立刻回查"。**

实测结论（自检页 A/B/C/D 四组对照）：

| 组 | 做法 | 结果 |
|---|---|---|
| A | 事务**外** `executeSql` 插入后回查主键 | ✅ 拿到 id |
| B | 事务**内** 同样写法 | ❌ 回查得 **0**，但提交后该行确实存在 |
| C | 事务**内** typed `store.insert()` | ✅ 直接返回 rowId |
| D | 事务**内** `executeSql` + `last_insert_rowid()` | ❌ 得 **0** |

即：**事务内 `querySql` 读不到同一事务刚写入的数据**（推测是连接池把查询派发到了另一条连接）。
`last_insert_rowid()` 也失效，说明这不是"按某列回查"的问题，而是事务内一切读取都看不到本事务的写入。

因此规定：
1. **需要主键时用 typed 接口**（`store.insert()` / `store.batchInsert()`）—— 它们直接返回 rowId，不查库
2. **事务内只允许"先读后写"**：读取必须发生在写入之前
3. 更新/删除类操作不需要主键，用 `executeSql` 即可
4. 这个坑极具误导性：错误信息是"写入失败"，但真相是"写入成功、读回失败"，
   很容易让人去排查 INSERT 语句或表约束。**排查时先做 A/B 对照（事务内 vs 事务外）**

### 4.2 表结构（6 张）

#### 表 1：`book`（书籍表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| uuid | TEXT | 稳定文件标识，用于沙箱文件名。**唯一索引** |
| title / author | TEXT | 书名 / 作者 |
| cover_path / file_path | TEXT | **沙箱相对路径**，不含 `filesDir` 前缀 |
| format | TEXT | `txt` / `epub`，带 CHECK |
| encoding | TEXT | `utf-8` / `gbk` / `gb18030` / `big5` / `utf-16le` / `utf-16be` |
| file_size / file_hash | INTEGER / TEXT | 字节数 / 原始文件字节的 SHA-256 |
| group_id | INTEGER | 外键 → `book_group.id`，可空 |
| total_chapters / word_count | INTEGER | 解析后汇总 |
| added_at / updated_at / last_read_at | INTEGER | 毫秒时间戳 |
| **last_chapter_index** | INTEGER | **0-based，-1 = 无进度** |
| last_offset | INTEGER | 章内 UTF-16 下标 |
| read_status | INTEGER | 0未读 1在读 2读完 |
| progress_percent | REAL | 0~1，冗余字段便于书架排序 |
| **location** | TEXT | JSON 兼容层，见下 |
| parse_status | INTEGER | 0待解析 1解析中 2成功 3失败 |
| parse_error / parse_rule | TEXT | 失败原因（含"文件丢失"）/ 命中的分章规则 |
| metadata | TEXT | 扩展元数据（EPUB OPF 等） |
| deleted | INTEGER | 软删除 |

**`location` JSON 契约（定死，不留自由发挥）**
```jsonc
{ "type": "txt", "chapterIndex": 12, "offset": 340, "percent": 0.213 }
{ "type": "epub", "href": "OEBPS/ch03.xhtml", "anchor": "p12", "cfi": "/6/4!/4/2", "percent": 0.213 }
```
`last_chapter_index` + `last_offset` 是**权威进度**；`location` 是与格式无关的兼容层，两处必须同源同事务写入。

> **决策记录：`file_path` 为什么存相对路径而不是绝对路径**
> `filesDir` 在应用升级/迁移后会变。存绝对路径的话，升级后所有书记录都指向不存在的文件，
> 表现是"书还在书架上、点开说文件丢失"，而且**不报错、没有异常堆栈**。
> 相对路径 + 运行时拼接是唯一稳妥的做法。

#### 表 2：`chapter`（章节表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| book_id | INTEGER | 外键 → `book.id`，`ON DELETE CASCADE` |
| title | TEXT | 章节标题（**不含换行符**） |
| **start_offset** | INTEGER | **原文件字节偏移，指向标题行之后的正文首字节** |
| **end_offset** | INTEGER | 原文件字节偏移（不含），等于下一章标题行首；末章为 NULL |
| href / anchor | TEXT | EPUB 用 |
| level | INTEGER | 0=章 1=卷 |
| word_count | INTEGER | 估算字数 |
| chapter_index | INTEGER | **0-based**，`UNIQUE(book_id, chapter_index)` |

> **⚠️ `start_offset` 必须指向标题行之后的正文首字节，而不是标题行本身**
>
> 这是实测踩到的坑：若 `start_offset` 取标题行首，第 1 章读出来会变成
> `"第一章 初入江湖\n这是第一章的正文。..."` —— 标题混进了正文。
> 而第 2 章之后恰好正常（因为上一章的 `end_offset` 把标题留在了上一章末尾），
> **所以这个 bug 只在第 1 章暴露，极易漏测**。
>
> 约定：
> - `chapter.title` 单独存标题文本，目录用；
> - `start_offset` = 标题行首字节 + 标题行含换行符的字节长度（`\r\n` 算两个字节）；
> - `end_offset` = 下一章标题行的首字节（因此本章末尾会带一个空行，属正常）；
> - 阅读页因此**不需要**再重复渲染标题。

#### 表 3：`annotation`（书签 / 划线 / 笔记表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| book_id / chapter_id / chapter_index | INTEGER | **`chapter_id` 是外键真相，另两列是查询冗余** |
| start_offset / end_offset | INTEGER | 章内 UTF-16 下标；书签可空（只记章首） |
| selected_text / note_content | TEXT | 选中文本 / 笔记内容 |
| type | INTEGER | 1书签 2划线 3笔记，带 CHECK |
| color | TEXT | 划线颜色 |
| created_at / updated_at / deleted | INTEGER | |

> **决策记录：为什么留 `book_id` / `chapter_index` 两个冗余列**
> 书签列表要按章排序、目录要按章聚合标记，若只留 `chapter_id` 就得每次 JOIN `chapter`。
> 代价是**三处必须一致** —— 所以新增标注时冗余列由 `AnnotationRepository.add()` 统一反查填充，
> **禁止业务层自己拼 INSERT**（三处不一致会让书签在目录里串章，且不报错）。

#### 表 4：`book_group`（分组表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| name | TEXT | 分组名，`UNIQUE WHERE deleted = 0` |
| sort_order | INTEGER | 越小越靠前 |
| created_at / updated_at / deleted | INTEGER | |

> **⚠️ `ON DELETE SET NULL` 在软删除下永远不会触发**
> 删除分组必须在事务里**手动**把成员 `group_id` 置 NULL，
> 否则会出现"书指向一个已删除的分组"而从书架消失。见 `GroupRepository.softDeleteWithMembers()`。

#### 表 5：`reading_daily_stats`（阅读统计表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| book_id | INTEGER | **0 = 全局统计**（哨兵值，不参与外键） |
| date | TEXT | `YYYY-MM-DD`，**本地时区** |
| duration_seconds | INTEGER | 阅读时长（秒） |
| updated_at | INTEGER | |

约束：`UNIQUE(book_id, date)`。

> **⚠️ 写入必须 upsert**：`INSERT ... ON CONFLICT(book_id, date) DO UPDATE SET duration = duration + excluded.duration`，
> 否则同一本书同一天会产生多条记录，"今天读了多久"时对时错。
> **⚠️ 日期用本地时区**：用 UTC 的话，晚上 8 点后的阅读会被算到"明天"，连续打卡天数会对不上。

#### 表 6：`page_cache`（分页缓存表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | 自增主键 |
| book_id / chapter_index | INTEGER | |
| layout_key | TEXT | 排版方案指纹，见下 |
| breaks | TEXT | 断点数组 JSON，元素为**章内 UTF-16 下标** |
| page_count | INTEGER | 冗余，便于快速显示 |
| updated_at | INTEGER | |

约束：`UNIQUE(book_id, chapter_index, layout_key)`。这是**纯派生数据**，可直接清空，不需要 `deleted` 列。

**`layout_key` 的计算口径（必须定死）**
```
w{内容宽}_h{内容高}_fs{字号}_lh{行距}_ps{段距}_ls{字距}_fi{首行缩进}_ff{字体}
```
用**可读字符串**而非哈希：单条缓存几百字节，存储压力可忽略；出问题时能直接在库里看出排版参数。

> **⚠️ 不要用 delta 编码存断点**
> `breaks` 与正文一一对应，保留**绝对值**。delta 方案下一处损坏会导致整章错位，
> 而绝对值最坏只是某一页不准。约定 `breaks[0] === 0`，第 i 页覆盖 `[breaks[i], breaks[i+1])`。

### 4.3 索引（15 条）

```sql
-- 书籍
CREATE UNIQUE INDEX uq_book_uuid ON book(uuid);
CREATE UNIQUE INDEX uq_book_hash ON book(file_hash) WHERE deleted = 0 AND file_hash <> '';
CREATE INDEX idx_book_shelf  ON book(deleted, last_read_at DESC);
CREATE INDEX idx_book_group  ON book(group_id, deleted);
CREATE INDEX idx_book_status ON book(deleted, read_status, last_read_at DESC);

-- 章节（UNIQUE(book_id, chapter_index) 已生成隐式索引，不再重复建）
CREATE INDEX idx_chapter_title ON chapter(book_id, title);

-- 标注
CREATE INDEX idx_annotation_book    ON annotation(book_id, chapter_index, deleted);
CREATE INDEX idx_annotation_chapter ON annotation(chapter_id, deleted);
CREATE INDEX idx_annotation_type    ON annotation(book_id, type, deleted);

-- 分组
CREATE UNIQUE INDEX uq_group_name ON book_group(name) WHERE deleted = 0;
CREATE INDEX idx_group_sort ON book_group(deleted, sort_order, id);

-- 统计（UNIQUE(book_id, date) 已覆盖 book_id 前缀查询）
CREATE UNIQUE INDEX uq_stats_book_date ON reading_daily_stats(book_id, date);
CREATE INDEX idx_stats_date ON reading_daily_stats(date);

-- 分页缓存
CREATE UNIQUE INDEX uq_page_cache ON page_cache(book_id, chapter_index, layout_key);
CREATE INDEX idx_page_cache_book ON page_cache(book_id);
```

> **⚠️ 两条索引刻意不建**（它们与各自的 UNIQUE 约束完全重复，只会拖慢批量导入）：
> `idx_chapter_book(book_id, chapter_index)` 与 `idx_stats_book(book_id, date)`。

> **⚠️ `idx_book_shelf` 为什么不是单列 `last_read_at DESC`**
> 书架查询**一定**带 `deleted = 0`。单列索引在这种查询下会被放弃（选择性差），
> 复合索引把主查询列放最前才有效。

### 4.4 写入路径（已定案）

| 操作 | 路径 | 原因 |
|---|---|---|
| 导入入库 | **单事务**：`insert(book)` → `batchInsert(chapter, 每 500 条)` → `updateParseState` | 要么全成要么全不成，避免"书在架但一章都没有"的僵尸记录 |
| 取新书主键 | `store.insert()` 的返回值 | 铁律 4 |
| 阅读进度 | 内存态 → 10 秒节流 / 切后台 / 退页时 `UPDATE book SET last_chapter_index, last_offset, location, progress_percent, last_read_at` | 不每页写库 |
| 阅读时长 | 事务内 upsert 两条：`book_id = 本书` 和 `book_id = 0`（全局） | 统计页与书籍详情各取所需 |
| 删除分组 | 事务内：先 `UPDATE book SET group_id = NULL`，再软删分组 | `ON DELETE SET NULL` 在软删除下不触发 |
| 软删除书籍 | `UPDATE book SET deleted = 1`，**沙箱文件保留** | 便于恢复 |
| 硬删除书籍 | `DELETE FROM book`，`chapter`/`annotation`/`page_cache` 由外键 CASCADE 带走 | 依赖外键真正生效（见 §5.6 第 6 条） |

### 4.5 版本迁移（两条独立机制）

| 机制 | 作用域 | 用途 |
|---|---|---|
| `DbConstants.SCHEMA_BUILD` | **开发期** | 编进库文件名（`novel_reader_b2.db`）。改 DDL 就 +1，等于换一个全新的库文件 |
| `DbConstants.DB_VERSION` + `RdbHelper.migrate()` | **发布后** | 在同一个库文件内按版本号补列/补表/补索引，保留用户数据 |

> **⚠️ 为什么必须有 `SCHEMA_BUILD`（实测踩坑）**
> `CREATE TABLE IF NOT EXISTS` **永远不会修改已存在的表**。
> 开发过程中一旦改过 DDL（例如给 `format` 补 `DEFAULT 'txt'`），设备上残留的旧库就与新代码不一致。
> 典型症状：插入时报 `SQLite: Abort due to constraint violation` ——
> 因为旧表没有 `format` 的默认值，省略该列时它成了 NULL，撞上 NOT NULL 或 CHECK。
> 这个错误极具误导性：看起来像代码写错了，实际上是表结构过期。
>
> **排查耗时一整轮，所以定成规矩：开发期改任何 DDL，必须把 `SCHEMA_BUILD` +1。**

**迁移规则**
1. `migrate()` 里每一步必须**幂等**，用户可能在迁移中途被杀进程
2. **只允许加列 / 加表 / 加索引**。SQLite 不支持改列类型或删列，
   真要改必须走"建新表 → 拷数据 → 换名"，属发布级破坏性变更，需单独评估
3. `RdbHelper.addColumnIfMissing()` / `hasColumn()` 已提供，直接复用

### 4.6 偏好设置（Preferences）

使用单个实例 `reader_settings`，全部 key 集中在 `SettingsKeys` 常量类中。

| 分类 | key |
|---|---|
| 元信息 | `schema_version`、`first_launch_done` |
| 排版 | `font_size` `font_family` `line_height` `paragraph_spacing` `page_margin` `letter_spacing` `first_line_indent` |
| 显示 | `page_mode` `theme` `bg_color` `keep_screen_on` `hide_status_bar` `volume_key_page` `brightness` |
| 书架 | `grid_mode` `book_sort` |
| TTS | `tts_speed` `tts_voice` `tts_timer_minutes` |

**三条约定**
1. **每个 getter 带默认值**（key 缺失时返回默认值），因此"漏写默认值"不会导致类型错误，首次启动也不需要批量初始化全部 key
2. **写设置逐项 `put` 而不是先 `clear()`**：`clear` 中途失败会把用户所有设置清空，逐项覆盖是幂等的
3. **写设置必须 `flush`**，否则只在进程被杀时暴露，开发期几乎看不出来

> **决策记录：为什么判据是"SQLite 存要查询/聚合/建索引的实体，Preferences 存永远只有一个值的单例配置"**
> 反过来（把设置做成表的行）会让每次读设置都过一次数据库；
> 而把书籍列表塞进 Preferences 则会失去索引与聚合能力。
> 另外**禁止**把单书设置写成动态 key（`book_3_fontsize`）—— 那会无限增长。

### 5.2 分层架构

```
页面层 (pages) → 视图组件层 (views) → 状态层 (viewmodels) → 服务层 (service) → 数据层 (repository) → SQLite
```

**分层依赖规则（只能向下，禁止反向）**

```
pages/  views/            View：只调用 ViewModel；禁止 import repository / database
      ↓
viewmodels/               ViewModel：调用 Service/Repository；禁止 import pages / views
      ↓
data/service/  data/repository/
      ↓
data/database/            只有 Repository 能 import
      ↓
model/  common/           纯数据与工具，谁都能用，自身不依赖任何人
```

**三条硬约束**
1. **View 不写业务逻辑**，也不出现 `relationalStore` / `fs` / `preferences`
2. **Repository 只返回 model 对象或状态码，绝不返回 `ResultSet`**
3. **ViewModel 不持有 UI 组件**；`Context` 由 `EntryAbility` 启动时注入，不在各处 `getContext()`

### 5.3 状态管理（ArkUI V1）

本项目用 **V1 观测体系**（`@State` / `@Prop` / `@ObjectLink` / `@Observed`）。

> **决策记录：为什么不用 V2（`@Local` / `@Param` / `@ObservedV2` / `@Trace`）**
> V2 的细粒度刷新确实更好，但参考项目实测出一个 V2 的关键限制（§5.6 第 37 条）：
> `@ComponentV2` 在 SDK 声明里**没有 `@form` 标记**，因此**服务卡片只能用 V1 写**。
> 本项目 P2 阶段要做「继续阅读」服务卡片，如果 App 侧全量上 V2，
> 就会出现"卡片 V1 + App V2"两套心智模型，且 `views/` 下的组件**一个都不能在卡片里复用**。
> 当前代码已按 V1 落地且自检通过，**故保持 V1**。
> 若后续放弃服务卡片，可整体迁移到 V2（迁移项见 §6）。

| 场景 | 本项目用法 |
|---|---|
| 页面内状态 | `@State` |
| 父子传值（需要跟随更新） | **`@Prop`** |
| 数据类深度观测 | `@Observed` + `@ObjectLink` |
| 跨页面版本号 | `AppStorage`（仅作诊断，刷新由根页面驱动） |

**三条硬约束**
1. **`@Prop` 不是可选项**：普通成员只在组件创建时取一次快照，
   父组件状态变了子组件不会更新（实测：进度条数字弹回去）。见 P2
2. **`@Observed` 对象的字段变化要能被观察到**：接收方必须用 `@ObjectLink`，
   普通 `@State` 只在顶层赋值时重绘
3. **同一个组件内部 V1/V2 不能混用**（SDK 限制，混用直接编译失败）

**一条工程习惯**：`@State` 只给**在 `build()` 里被读到的**变量用。
只在方法里用、不参与渲染的字段声明成普通 `private` 成员 —— 否则每次改它都会触发一次无意义的 `build()` 重跑。

### 5.4 状态刷新的正确姿势

**这是本项目踩坑最多的地方，单独成节。**

| 我依赖过的机制 | 是否可靠 | 原因 |
|---|---|---|
| 子页面 `onPageShow` | ❌ | **只对 `@Entry` 页面触发**，普通 `@Component` 拿不到 |
| `AppStorage` 版本号 + `setInterval` 轮询 | ❌ | 定时器在 `aboutToDisappear` 里被清掉，而 Tab 切换**不保证重新 `aboutToAppear`** → 定时器一死就再也没刷新过 |
| `AppStorage.link().onChange` | ❌ | `SubscribedAbstractProperty` **没有 `onChange` 属性**（想当然了） |
| **根页面 `onPageShow` + Tabs `onChange`** | ✅ | 只有 `@Entry` 页面拿得到，且覆盖"从阅读页返回"与"切回 Tab"两个场景 |
| **`TabContent.onWillShow`**（推荐迁移） | ✅ | `@since 12`，声明明确覆盖 first-time display / tab switching / page switching / 前后台切换，覆盖面最全 |

**当前实现（已通过自检）**：根页面驱动 + `ShelfRefreshRegistry`。
**迁移项**：改用 `TabContent.onWillShow`，按 Tab 各持一个 `reloadTick` 计数器（避免一个 Tab 刷新连带另一个白查库）。

### 5.5 存储底座初始化

**问题**：`PathUtil` / `RdbHelper` / `SettingsService` 都需要 Context，而 ViewModel 里拿不到 Context。
**又**：`SettingsService` 的 getter 是**同步**的，`store` 为 null 时会抛错。

**方案：可自愈的幂等初始化**

```
EntryAbility.onCreate
  └── StorageBootstrap.bootstrap(context)   注入 Context，启动初始化（不阻塞窗口创建）
        ├── PathUtil.init(ctx)
        ├── RdbHelper.init(ctx)
        └── SettingsService.init(ctx)

每个服务自己持有 ensureReady()（幂等，缓存 Promise）
  - RdbHelper.ensureReady()      在 queryNumber / query / queryFirst / withTransaction 内部自动调用
  - SettingsService.ensureReady()
```

**页面侧必须显式门控**（这是实测踩到的坑）：

```ts
aboutToAppear(): void {
  this.vm.bind(this.state);
  // 必须先等存储就绪，再让 ViewModel 读设置
  StorageBootstrap.ensureReady().then(() => {
    this.vm.init();
  }).catch((e: Object) => {
    this.state.error = `初始化失败：${Logger.errText(e)}`;
  });
}
```

> **⚠️ 直接调 `this.vm.init()` 会抛 "SettingsService 尚未初始化"**
> `vm.init()` 一进来就要读 `gridMode` / `bookSort`，而 `SettingsService.init()` 还没跑完。
> **依赖顺序的地方，要让调用结构保证顺序，而不是靠"我记得先调这个"。**

### 5.7 主题设计

**核心问题：颜色一旦写死在页面里，深色模式就没法做。**
所以第一步不是配色，而是**语义令牌 + 资源引用**。

#### 5.7.1 三层结构

```
第 1 层  语义令牌     resources/base/element/color.json + resources/dark/element/color.json
                     ↓ 页面只引用 $r('app.color.xxx')，绝不写 hex
第 2 层  组件主题类   common/theme/AppTheme.ets（尺寸/圆角/字号）
                     ↓ 供 ArkUI 属性使用；颜色也在此集中引用资源
第 3 层  阅读页配色   common/theme/ReaderTheme.ets（四套配色，见 5.7.3）
```

> **为什么阅读页配色不走资源令牌**
> 阅读页的配色是**用户选择**的（浅色/羊皮纸/护眼/夜间），不是"跟随系统深浅模式"。
> 用资源令牌的话，系统切深色会和用户选择打架。
> 所以阅读页的 `bg` / `text` / `secondary` / `barBg` 走 `ReaderTheme.of(userChoice)` 返回的**普通 class**，
> 而 App 其余部分（书架、设置、我的）走资源令牌跟随系统。

#### 5.7.5 深色模式的实现要点

1. **目录结构**：`resources/base/element/color.json`（浅色）+ `resources/dark/element/color.json`（深色），
   同名令牌自动切换 —— 这是系统能力，不需要手写判断
2. **必须在 `EntryAbility.onCreate` 里用同步读法设好主题**：
   `Preferences` 的 `getPreferencesSync` + `getSync` 是同步 API（`@ohos.data.preferences.d.ts:451/1113`）。
   走异步的话系统会先按默认主题画一帧 —— 深色模式下就是"黑底应用先闪一下白屏"
3. **自己的枚举和平台枚举数值不同时，转换只允许在一处做**：
   ```
   应用 ThemeMode:           平台 ConfigurationConstant.ColorMode:
     FOLLOW_SYSTEM = 0         COLOR_MODE_NOT_SET = -1
     LIGHT         = 1         COLOR_MODE_DARK    =  0
     DARK          = 2         COLOR_MODE_LIGHT   =  1
   ```
   顺序都不一样。**哪里图省事直接把自己的值传给平台，浅色/深色就会反掉，而且不报错。**
   转换收在 `ThemeApplier.applyThemeMode()` 一处
4. **换主题的顺序是「先应用、再落盘」**：反过来的话，万一 `setColorMode` 失败，
   设置已经存下来了，下次启动才生效 —— 用户看到"点了没反应，重启以后变了"，比直接失败更难理解
5. **⚠️ 本项目的特殊情况**：书架/阅读页已有自己的配色逻辑，
   接入令牌前必须先**清掉页面里的 hex 字面量**。当前 `AppTheme` 里的色值就是 hex 字符串
   （`static readonly PRIMARY: string = '#3B6FE0'`）——**这是待改造项**，
   要改成 `brand: Resource = $r('app.color.brand')` 的形态，否则深色模式不会生效

## 6. 风险清单与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| **大文件解析卡主线程**（10 MB+ 需数秒） | 🔴 高 | 必须有可见进度文案（已做）；**彻底解法是 `taskpool`**，要求解析器与文件访问可序列化 —— 列为本轮之后的优化项 |
| **自动编码识别不可能 100% 准确** | 🔴 高 | 已做：分层探测 + 逐层校验（可读文本占比 ≥ 0.98）；已做：**换编码重解析**，让用户自救而不必重新导入 |
| **`views/` 组件无法在服务卡片复用** | 🟡 中 | V2 迁移后可复用，但卡片本身只能用 V1（§5.6 第 37 条相关）。**当前决定：放弃"卡片复用组件"，卡片单独写** |
| **刷新机制需要迁移到 `TabContent.onWillShow`** | 🟡 中 | 当前根页面驱动已能工作；迁移后覆盖面更全，且支持按 Tab 独立刷新计数 |
| **深色模式尚未接入** | 🟡 中 | 令牌与 `AppTheme` 改造是**前置依赖**（§5.7.6），否则做了也不生效 |
| **换编码会删除书签/笔记** | 🟡 中 | 当前只在菜单标题里告知数量，**书签功能上线前必须补二次确认弹窗** |
| **重解析与删除书籍之间可能竞态** | 🟡 中 | 长任务期间应禁用该书的其他操作；当前靠"重解析中"状态位提示，未做按钮禁用 |
| **无真机验证** | 🔴 高 | 优先用模拟器；长时任务、TTS 等系统能力必须真机验证 |
| **上架合规** | 🟢 低 | 零联网、零权限、零第三方 SDK —— 审核优势，但需准备隐私政策页 |
| **排期紧** | 🟡 中 | 书签/搜索/统计/备份均列为 P1，可砍 |
