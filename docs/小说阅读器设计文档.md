## 五、数据模型与存储（核心修订）

### 5.1 三条铁律（写代码前必须遵守）

**铁律 1：`chapter_index` 一律 0-based，"无进度"用 `-1`。**
初版 `chapter` 表写"从 1 开始"，而 `book.last_chapter_index` 默认 `0` 表示无进度 —— 于是 `0` 同时是"无进度"和"第一章"，只要有一处用 `chapters[chapter_index]` 取值就整体错位一位。
本版统一：**0-based，与数组下标一致；`-1` 表示无进度**。UI 展示时再 `+1`。

**铁律 2：偏移量单位分两种，不得混用。**

| 用途 | 单位 | 说明 |
| --- | --- | --- |
| `chapter.start_offset` / `end_offset` | **原文件字节偏移** | 用于 `fs.read(fd, buf, {offset})` 随机读。字节单位才有 seek 能力，读到的字节仍按 `encoding` 解码，与文件编码无关 |
| `annotation.start_offset/end_offset`、`page_cache.breaks`、`ReadingPosition.offset` | **章内解码文本的 UTF-16 代码单元下标** | 即 ArkTS `string` 的天然索引。选文用 `Text` 的 `onTextSelectionChange` 拿到的下标同源，可直接对应 |

注意：UTF-16 代码单元在含 emoji / 生僻字（代理对）时与"字符数"不等，但**与 JS 字符串下标一致**，这是唯一能与 UI 选区对齐的口径。`word_count` 另按代码点统计（见 5.3），不要混用。

**铁律 3：进度绝不存页码。**
页码不是稳定量 —— 字号、字体、行距、边距、屏幕宽度、折叠屏形态任一变化，页边界全部改变。
进度只存 **`章节序号 + 章内偏移 + 百分比`**，页码在当前分页方案下即时推算。

**铁律 4：事务内禁止"写完立刻回查"。**

实测结论（自检页 A/B/C/D 四组对照，见附录 C）：

| 组 | 做法 | 结果 |
| --- | --- | --- |
| A | 事务**外** `executeSql` 插入后回查主键 | ✅ 拿到 id |
| B | 事务**内** 同样写法 | ❌ 回查得 **0**，但提交后该行确实存在 |
| C | 事务**内** typed `store.insert()` | ✅ 直接返回 rowId |
| D | 事务**内** `executeSql` + `last_insert_rowid()` | ❌ 得 **0** |

即：**事务内 `querySql` 读不到同一事务刚写入的数据**（推测是连接池把查询派发到了
另一条连接，看不到未提交的行）。`last_insert_rowid()` 也失效，说明这不是
"按某列回查"的问题，而是事务内一切读取都看不到本事务的写入。

因此规定：

1. **需要主键时用 typed 接口**（`store.insert()` / `store.batchInsert()`）——
   它们直接返回 rowId，不查库。`BookRepository.insert`、`AnnotationRepository.add`、
   `GroupRepository.insert` 都改成了这种写法。
2. **事务内只允许"先读后写"**：读取必须发生在写入之前。例如
   `GroupRepository.softDeleteWithMembers` 先 `memberIds()` 再逐个 `UPDATE`，这是合法的。
3. 更新/删除类操作不需要主键，用 `executeSql` 即可，不受影响。
4. 这个坑极具误导性：错误信息是"写入失败"，但真相是"写入成功、读回失败"，
   很容易让人去排查 INSERT 语句或表约束。排查时先做 A/B 对照（事务内 vs 事务外）。

### 5.2 存储职责划分

| 存储 | 放什么 | 不放什么 |
| --- | --- | --- |
| 沙箱文件 | 原始书籍文件、封面图、解析文本缓存 | 结构化数据 |
| RDB | 书籍、章节、标注、分组、统计、分页缓存 | 用户设置 |

沙箱目录规划（`context.filesDir` 下，RDB 只存**相对路径**，不存绝对路径 —— 绝对路径在应用升级/迁移后会失效）：

```
filesDir/
├─ books/<book_uuid>.txt          # 原始导入文件
├─ covers/<book_uuid>.jpg         # 封面（TXT 无封面时为空）
├─ parsed/<book_uuid>.chapters.json  # 分章结果备份（可选，用于重解析）
└─ backup/                        # 备份导出临时目录
```

### 5.3 表结构

#### 统一约定

- 所有时间戳为**毫秒级 `INTEGER`**（`Date.now()`）。
- 所有布尔字段用 `INTEGER` + `CHECK (x IN (0,1))`。
- **所有删除都按"软删除优先"**：`book`、`chapter`、`annotation`、`book_group` 有 `deleted`；`page_cache` 是纯缓存，直接物理删除；`reading_daily_stats` 是累计统计，不做删除。
- 连接后必须执行 `PRAGMA foreign_keys = ON`（RDB 默认关闭）。

**`location` JSON 结构（定死，不留自由发挥）**

```jsonc
// TXT
{ "type": "txt", "chapterIndex": 12, "offset": 340, "percent": 0.213 }
// EPUB（V1.1）
{ "type": "epub", "href": "OEBPS/ch03.xhtml", "anchor": "p12", "cfi": "/6/4!/4/2", "percent": 0.213 }
```

规则：
- `last_chapter_index` + `last_offset` 是**权威进度**；`location` 是与格式无关的**兼容层**，两处写入必须同源同事务。
- `progress_percent` 由 `location.percent` 同步。

**约束与索引**

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_book_uuid ON book(uuid);
CREATE UNIQUE INDEX IF NOT EXISTS uq_book_hash ON book(file_hash) WHERE deleted = 0 AND file_hash <> '';
CREATE INDEX IF NOT EXISTS idx_book_shelf   ON book(deleted, last_read_at DESC);
CREATE INDEX IF NOT EXISTS idx_book_group   ON book(group_id, deleted);
CREATE INDEX IF NOT EXISTS idx_book_status  ON book(deleted, read_status, last_read_at DESC);
```

> 修订说明：
> ① 原 `idx_book_last_read ON book(last_read_at DESC)` 单独一列没有意义 —— 书架查询**一定**带 `deleted = 0`，改为主查询列在前的复合索引。
> ② 原方案"file_hash 去重"没有唯一约束兜底，并发导入可产生重复书；这里用**部分唯一索引**（只约束未删除且非空哈希的行），既保证去重又允许软删除后重新导入。
> ③ 新增 `parse_status`/`parse_error`/`parse_rule`：大 TXT 解析是耗时操作，必须能异步化、能失败、能重试、能换规则重解析。初版无此字段，解析中断就会留下一本永远只有 0 章的书。

> **`file_hash` 去重的三种命中情形（必须分别处理，否则用户会遇到"导入没反应"）**
>
> | 命中情况 | 行为 |
> | --- | --- |
> | 哈希命中**未删除**的书 | 提示"本书已在书架"，跳转该书详情，不新建 |
> | 哈希命中**已软删除**的书 | 弹窗让用户选：**恢复该书**（`deleted = 0`）或**作为新书导入** |
> | 哈希为空（旧数据/计算失败） | 跳过哈希判重，按标题+大小给出弱提示即可 |
>
> **文件生命周期**：软删除只标记 `deleted = 1`，**沙箱文件不立即删除**，因此"回收站/恢复"可行；但需要一条清理策略（例如"设置 → 清除缓存"里提供"清理已删除书籍的文件"），否则删除的书会白占磁盘。
> 反过来，若用户手动删除或系统清理了沙箱文件，读取时 `fs.access` 失败 → 将该书 `parse_status = 3`、`parse_error = "文件丢失"`，详情页给出"重新导入"入口。**这是必须实现的路径**，初版只在界面清单里列了"文件丢失"，没有对应的数据落点。

> ② 初版 `start_offset` 注释为"TXT 字符偏移"，改为**字节偏移**，否则 `.txt` 无法用 `fs.read` 直接 seek（铁律 2）。
> ③ 初版建议的 `idx_chapter_book(book_id, chapter_index)` 与 `UNIQUE(book_id, chapter_index)` **完全重复**，纯属多一份写入开销且拖慢批量导入 —— **已删除**；额外补 `title` 索引供"章节标题搜索"用。

> **`start_offset` 必须指向标题行之后的正文首字节，而不是标题行本身。**
>
> 这是实测踩到的坑：若 `start_offset` 取标题行首，则第 1 章读出来会变成
> `"第一章 初入江湖\n这是第一章的正文。..."` —— 标题混进了正文。
> 而第 2 章之后恰好正常（因为上一章的 `end_offset` 把标题留在了上一章末尾），
> 所以这个 bug 只在第 1 章（或"前言"缺失时）暴露，很容易漏测。
>
> 约定：
> - `chapter.title` 单独存标题文本，目录用；
> - `start_offset` = 标题行首字节 + 标题行含换行符的字节长度（`\r\n` 算两个字节）；
> - `end_offset` = 下一章标题行的首字节（因此本章末尾会带一个空行，属正常）；
> - 阅读页因此**不需要**再重复渲染标题。

> **口径统一**：`total_chapters` / `word_count` 统计的是 **`chapter` 表中该书的全部行**。
> `chapter` 只随书籍整体删除（走 `ON DELETE CASCADE`），不做单章删除；如需重解析，在事务内
> `DELETE FROM chapter WHERE book_id = ?` 后整体重建，保证三个字段永远自洽。

#### 表 6 · `page_cache` 分页缓存表【本版新增】

初版第三节、第六节都提到"缓存分页结果"，但数据模型中**没有任何地方放它** —— 这是初版最实质的结构性缺口。

| 字段 | 中文 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- | --- |
| id | 缓存ID | INTEGER | 是 | 自增 | 主键 |
| book_id | 书籍ID | INTEGER | 是 | — | |
| chapter_index | 章节序号 | INTEGER | 是 | — | 0-based |
| layout_key | 排版方案指纹 | TEXT | 是 | — | 见下 |
| breaks | 分页断点 | TEXT | 是 | `''` | 章内 UTF-16 下标数组 JSON |
| page_count | 页数 | INTEGER | 是 | 0 | 冗余，便于快速显示 |
| updated_at | 更新时间 | INTEGER | 否 | NULL | |

**`layout_key` 的计算口径（必须定死）**：对以下影响排版的参数做归一化后取 SHA-256 前 16 位。

```
textWidth, textHeight, fontSize, fontFamilyHash, lineHeight, paragraphSpacing,
letterSpacing, firstLineIndent, padding
```

**约束与索引**

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_page_cache ON page_cache(book_id, chapter_index, layout_key);
CREATE INDEX IF NOT EXISTS idx_page_cache_book ON page_cache(book_id);
```

> 设计要点：
> ① **不在 `book` 里存"当前排版指纹"**。原因：换字号后旧缓存仍然对新字号无效、对新字号又是新 key，存了也只为省一次计算；而**用 `offset` 反查页**本身只需要遍历断点数组（`breaks[i] <= offset < breaks[i+1]` → 第 i 页），**根本不需要知道旧指纹**。少一个字段、少一处不一致。
> ② `breaks` 是与正文一一对应的断点数组（**章内 UTF-16 下标**，保留绝对值、不用 delta，避免一处损坏导致整章错位），如 `[0,412,830,1240]` 表示第 0~411 字符为第 1 页；5000 字符的章节约 40 个断点，单行几百字节，无存储压力。
> ③ `page_cache` 是**纯派生数据**，物理删除即可，不需要 `deleted` 列。
> ④ "清除缓存"功能 = `DELETE FROM page_cache` + 清 `filesDir/parsed`，不影响任何用户数据。

### 5.5 版本迁移策略

RDB 必须显式管理版本，否则后续加字段（EPUB、TTS 字段等）无法平滑升级。
本方案分**两条独立的机制**，职责不要混淆：

| 机制 | 作用域 | 用途 |
| --- | --- | --- |
| `DbConstants.SCHEMA_BUILD` | **开发期** | 编进库文件名（`novel_reader_b2.db`）。改 DDL 就 +1，等于换一个全新的库文件 |
| `DbConstants.DB_VERSION` + `migrate()` | **发布后** | 在同一个库文件内按版本号补列 / 补表 / 补索引，保留用户数据 |

> **为什么必须有 SCHEMA_BUILD**（实测踩坑）：
> `CREATE TABLE IF NOT EXISTS` **永远不会修改已存在的表**。
> 开发过程中一旦改过 DDL（例如把 `last_chapter_index` 的默认值从 `0` 改成 `-1`、
> 或给 `format` 补上 `DEFAULT 'txt'`），设备上残留的旧库就与新代码不一致。
> 典型症状：插入时报 `SQLite: Abort due to constraint violation` ——
> 因为旧表没有 `format` 的默认值，省略该列时它成了 NULL，撞上 `NOT NULL` 或
> `CHECK (format IN ('txt','epub'))`。
> 这个错误极具误导性：看起来像代码写错了，实际上是表结构过期。
> 用构建号命名库文件可以从根上杜绝这类问题。

```
SCHEMA_BUILD = 2      // 每次改 DDL 都要 +1
DB_VERSION   = 1      // 发布后才需要动

onCreate  : 执行 5.4 全部 DDL（幂等）
onUpgrade : v1 → v2（发布后）:
            await this.addColumnIfMissing('book', 'tts_voice', "TEXT NOT NULL DEFAULT ''");
```

规则：
1. `migrate()` 里每一步必须**幂等**，用户可能在迁移中途被杀进程。
2. **只允许加列 / 加表 / 加索引**。SQLite 不支持改列类型或删列，
   真要改必须走"建新表 → 拷数据 → 换名"，属发布级破坏性变更，需单独评估。
3. `RdbHelper.addColumnIfMissing()` / `hasColumn()` 已提供，直接复用。

### 5.7 全书搜索的实现路线（P1，前期不必建表）

章节正文**不存在数据库里**（只存偏移），所以"全书搜索"不属于本版数据模型，但必须提前定路线，否则 V1.1 会想当然地写出一条全表扫描的慢查询。

**已核实的 SDK 能力**：`relationalStore.StoreConfig` 支持 `tokenizer` 与 FTS 共享库，提供 `Tokenizer.ICU_TOKENIZER` / `CUSTOM_TOKENIZER`，并有 `relationalStore.isTokenizerSupported(tokenizer)` 可在运行时探测。

**推荐实现（按成本从低到高）**

| 阶段 | 方案 | 代价 |
| --- | --- | --- |
| V1.1 最小实现 | 顺序流式读文件（复用导入期的分块解码）逐章 `indexOf`，命中即返回并**可取消**；结果只保当前书的章节序号+偏移列表 | 无额外存储，一本 5 MB 的书约需 1~3 秒，配合进度条可接受 |
| 体验优化 | 为每本书建一条独立 FTS 表 `fts_book_{id}`（`CREATE VIRTUAL TABLE ... USING fts5(content, tokenize='icu')`） | 存储翻倍（约等于正文大小），需处理构建与失效 |
| 不建议 | `SELECT content FROM chapter WHERE content LIKE '%kw%'` | 正文不在库里；若真把正文入库，等于存储翻倍且必须全表读，反而更慢 |

**结论**：P1 先用流式 `indexOf` + 可取消，**不新增表**；只有当用户反馈慢时才引入 FTS 虚表，且届时用 `isTokenizerSupported` 先探测分词器可用性，不可假定 `ICU_TOKENIZER` 在所有设备上都存在。

### 5.8 实体关系

## 六、TXT 导入与解析流水线

这是整个项目**最大的技术风险点**，初版只有"编码识别和章节正则"一句，本版展开。

### 6.1 完整步骤

```
1. DocumentViewPicker.select({ fileSuffixFilters: ['.txt'] })
   → 得到临时授权 URI（经 picker 选择，通常无需额外申请读媒体权限）

2. fs.open(uri, READ_ONLY) + fs.stat → 取文件大小
   （若体积超过阈值，先提示用户）

3. 计算 SHA-256（流式，禁止整读）→ 按 §5.3 的 `file_hash` 去重三分支处理
   → 命中未删除的书：提示已存在并跳转；命中已软删除的书：让用户选"恢复"或"作为新书导入"

4. fs.copyFile(uri, filesDir/books/<uuid>.txt)
   → 复制到沙箱，避免 URI 授权失效后文件不可用

5. 编码探测（见 6.2）→ 低置信度时进入导入确认页让用户选择
   → 确认页展示解码后的前 N 行预览，肉眼可判

6. 分章解析（见 6.3）→ 边解析边收集 chapter 记录

7. 事务内 batchInsert 写 chapter、更新 book（total_chapters / word_count /
   parse_status = 2）；失败则 rollBack + parse_status = 3 + parse_error
```

### 6.2 编码探测方案（已按 SDK 修正）

**关键结论**：`util.TextDecoder` 只覆盖 UTF-8 / UTF-16LE / UTF-16BE / ISO-8859 / Windows-1251，**不含 GBK**；
而 **`util.StringDecoder` 明确支持 `gbk`、`gb18030`、`big5`、`koi8-r`、`windows-1250/1251`、`utf-16be/le` 等，且其 `write(Uint8Array)` 会自动过滤并缓存末尾不完整的多字节字符**。

→ 因此 TXT 导入**统一使用 `util.StringDecoder`**，既解决 GBK 解码，也天然解决分块读取的跨块残字节问题（初版担心的"多字节字符跨缓冲区"由它内部处理，无需自己拼残字节）。

探测顺序（每步给出置信度，最终统一交给用户确认）：

```
1. BOM 检测（最高置信度，直接定）
   EF BB BF → utf-8  ;  FF FE → utf-16le  ;  FE FF → utf-16be

2. UTF-8 合法性校验（置信度：高）
   取前 4 MiB，用 util.TextDecoder.create('utf-8', { fatal: true }) 试解
   （用 create 而非已废弃的带参构造函数）
   不抛错 → utf-8；抛错 → 进入第 3 步

3. 中文编码对照打分（置信度：中）
   同一段样本分别用 'gb18030' 与 'big5' 的 StringDecoder 解码，统计：
     - U+FFFD 替换字符数量（越少越好）
     - CJK 统一表意文字（U+4E00–U+9FFF）占比（越高越好）
     - 常见高频汉字命中率（的/一/是/了/不/在/人/有）
   取分高者；两者接近 → 置信度低 → 要求用户手选

4. 兜底：导入确认页提供 UTF-8 / GBK / GB18030 / BIG5 / UTF-16LE / UTF-16BE 下拉框
```

**GB18030 优先于 GBK**：GB18030 是 GBK 的超集，对 GBK 文件同样能正确解码，且能覆盖生僻字。
即：**默认用 `gb18030` 解码，而不是 `gbk`**；只有用户明确选择时才用 `gbk`。

### 6.3 分章策略

分两级正则，先高置信度后启发式，命中规则名写入 `book.parse_rule`：

| 级别 | 规则名 | 示例 |
| --- | --- | --- |
| L1 | `cn_chapter` | `第[一二三四五六七八九十百千零两0-9]+[章节回]` + 可选标题 |
| L1 | `cn_volume` | `第[...]+[卷部篇]` → `level = 1` |
| L1 | `en_chapter` | `^Chapter\s+\d+` / `^CHAPTER\s+[IVXLC]+` |
| L2（兜底） | `blank_line_heuristic` | 前后为空行、长度 < 40 字、不以标点结尾的短行 |
| L2（兜底） | `fixed_size` | 每 N 千字切一章（兜底保底，保证任何文件都能读） |

算法要点：

1. **单次顺序流式扫描**：`fs.createStream` 分块读（1 MiB/块）→ `decoder.write(chunk: Uint8Array)`。

2. **字节偏移 ↔ 字符偏移的映射**（初版完全缺失，必须实现，否则无法把"第 N 章在文本中的位置"换算成可 seek 的文件字节偏移）。
   原理：`StringDecoder` 会把末尾不完整的多字节字符留在内部缓冲，下次 `write` 时再交付。
   因此对**已交付的字符串**，其对应字节数 = 本次喂入前累计喂入字节 − 当前滞留字节。滞留字节数可如下精确计算：

   ```
   feedBytes   += chunk.byteLength
   pendingBytes = encoder.encode(decoder.write(chunk)).byteLength   // 用与解码同名的编码
   deliveredBytes = feedBytes - pendingBytes                        // 已交付文本在文件中的末尾字节位置
   ```

   其中 `encoder` 是 `new util.StringEncoder(encoding)`（与解码编码一致）。
   `deliveredBytes` 与"本次 `write` 返回字符串的末尾"严格对应，于是：

   ```
   章首文件字节偏移 = deliveredBytes_beforeThisChunk + localByteLen(该章标记之前的文本)
   ```

   实战简化：直接把每个块的 `write` 返回值**按 `\n` 切行**，逐行累加该行的字节长度（`encoder.encode(line).byteLength`）来推进一个
   `lineStartBytes` 游标；章首行的游标值即为 `chapter.start_offset`。这样既不需要全局映射表，也不会累积浮点误差。
   **注意**：`\r\n` 必须按原样计入字节长度，不能先归一化再计数，否则偏移会逐行漂移。

3. **规则只对行首生效**：正则锚定 `^`，避免正文中"第一章"被误判。
4. **过滤噪声**：单行命中数超过总行数 50% 视为误命中，降级到 L2。
5. **首章补全**：第一个章节标记之前若有内容（书名/简介），补一条 `chapter_index = 0`、`title = "前言"` 的记录，避免开头内容读不到。

### 6.4 大文件与性能

| 问题 | 处理 |
| --- | --- |
| 20 MB 以上的 TXT | 在 `taskpool` 中执行解析（RDB 写入仍在主线程串行），UI 显示进度条；可取消 |
| 章节逐条 insert | **必须** `beginTransaction` + `batchInsert`（每 500 条一批），否则数千章会非常慢 |
| 内存 | 全程只驻留单块（1 MiB）+ 当前章节文本，**禁止** `fs.readText` 整读 |
| 阅读时分章寻址 | `fs.open` 一次拿 fd，按 `chapter.start_offset` 读该章字节区间后解码；同一章内翻页复用已解码字符串 |

## 七、分页与进度

### 7.1 分页算法

```
可用高度 H = 容器高度 - 上下边距 × 2
行高       = fontSize × lineHeight
每页行数 L = floor(H / 行高)
每行字数 C = floor(可用宽度 / (fontSize + letterSpacing))
每页字数 P = L × C
```

按 `P` 对**段落数组**（先按 `\n` 切分并剔除空段）装箱：整段能放下就整段放，放不下则按 `C` 切行，保证段落首行缩进与行内不断字。

- 断点记录的是**章内 UTF-16 下标**，写入 `page_cache.breaks`。
- 每次换字号 / 旋转屏幕 / 改边距 → `layout_key` 变化 → 缓存 miss → 重算当前章并写入新 key。
- 重算要做**防抖**（300ms），避免拖滑块字号时疯狂重算。
- **只缓存已读过的章节**，不要导入时全书预分页（几千章全算一遍会非常慢且大部分用不到）。

### 7.2 进度保存与恢复

**保存时机（节流，不每页写库）**
- 翻页时更新内存中的 `ReadingPosition`；
- 以下事件触发落库：每 10 秒定时、`onBackground`、退出阅读页、切换章节；
- 落库内容：`last_chapter_index`、`last_offset`、`location`、`progress_percent`、`last_read_at`、`read_status`，**同一事务内更新**。

**恢复算法**

```
1. 读 book.last_chapter_index / last_offset
   -1 → 从第 0 章第 0 页开始
2. 定位章节 → 解码该章文本
3. 用当前 layout_key 查 page_cache.breaks
   - 命中 / 未命中（未命中则先重算分页并写缓存）
   - 定位公式：i = 满足 breaks[i] <= offset 的最大下标 → 显示第 i 页
     实现即 upper_bound(offset) - 1，等价于"最后一个断点 ≤ offset 的页"
     ⚠️ 不要写成"首个 breaks[i] > offset 的页" —— 当 offset 恰好落在某页
        断点上时会多翻一页，是典型的 off-by-one
4. UI 百分比用 book.progress_percent（跨章节的全局比例），
   不要用"当前页 / 当前章页数"（换字号会跳变，用户会以为进度丢了）
```

> 这里解释了为什么**不需要**在 `book` 里存"上次的排版指纹"：定位靠 `offset → 断点数组`，与旧排版无关。

### 7.3 阅读时长统计

- 进入阅读页记 `startTs`；`onBackground` / 退出时累计时长。
- 同时更新两条记录：`book_id = 本书` 和 `book_id = 0`（全局），用 `ON CONFLICT` upsert。
- **空闲判定**：无操作超过 5 分钟则暂停计时（避免挂着不读也算时长）。
- 连续阅读天数 = 从今天往前回溯 `reading_daily_stats` 中 `book_id = 0` 且 `duration_seconds > 0` 的连续日期数。

**分层依赖规则（只能向下，禁止反向）**

```
pages/  views/            View：只调用 ViewModel；禁止 import repository / database
      ↓
viewmodels/               ViewModel：调用 Service/Repository；禁止 import pages / views
      ↓
data/service/  data/repository/
      ↓

      ↓
model/  common/           纯数据与工具，谁都能用，自身不依赖任何人
```

三条硬约束：
1. **View 不写业务逻辑**，也不出现 `relationalStore` / `fs` / `preferences`。
2. **Repository 只返回 model 对象或状态码，绝不返回 `ResultSet`。**
3. **ViewModel 不持有 UI 组件**；`Context` 由 `EntryAbility` 在启动时注入，不在各处 `getContext()`。

**跨页面状态刷新（方案 A：AppStorage 版本号广播）**

`model/AppState.ets` 定义版本号 key。Repository / Service 在写操作成功后自增对应版本号；
书架等 ViewModel 监听该 key，一旦变化就重新加载。这样阅读页改了进度、导入完成了新书，
书架都会自动刷新，页面之间不需要互相引用，也不需要事件总线。

**状态更新机制**：ViewModel 内部的状态对象用 `@Observed` 装饰，View 用 `@ObjectLink` 接收。
注意：View 若只用 `@State` 持有 ViewModel **实例**，实例内部字段变化**不会**触发重绘 ——
这是 ArkUI 最常见的坑。

**路由**：采用 `@Entry` 页面 + `router`（DevEco 标准做法）。
`pages/Index.ets` 是根页面，内部用底部 `Tabs` 承载书架/统计/我的；
阅读页等通过 `router.pushUrl` 进入，并登记在 `resources/base/profile/main_pages.json`。

> 为什么不用 Navigation + NavPathStack：那样需要把 `ReaderPage` 等注册成
> `NavDestination`，且不能在非 `@Entry` 文件里 `import` 另一个 `@Entry` 页面
> （ArkTS 不允许）。`router` 方案下每个页面都是独立的 `@Entry` 文件，互不 import，
> 依赖关系更干净。`main_pages.json` 目前登记 `Index` / `ReaderPage` / `SelfCheckPage`。

**状态传递**：`@Observed` 状态对象由**根页面**持有并传给子页面，
子页面用 `@State` 接收 —— 这样 Tabs 切换导致子页面销毁重建时，
滚动位置与分组选择不会丢。ViewModel 由子页面自建并 `bind(state)`，
因为它只依赖状态与 Repository，没有额外状态需要跨页面保留。

### 8.4 ArkTS 约束（会频繁踩坑）

1. **严格静态类型**：无 `any`，无结构化类型，对象字面量必须有明确 `interface`/`class` 类型。
2. **页面 `build()` 中禁止做 DB 查询**，所有 IO 走 `async/await` + `@State` 回填。
3. `Repository` 层**统一封装软删除条件** `WHERE deleted = 0`，禁止页面直接拼 SQL（漏一处就是 bug）。
4. `LazyForEach` 需实现 `IDataSource`，目录列表的 `keyGenerator` 用 `chapter_index`，不要用可变的运行时变量。
5. 所有 DB 写操作走单例队列串行化，避免事务嵌套。

## 附录 C · 实测踩坑记录与尚待验证事项

### C.1 已踩到的坑（都已修，记下来避免重犯）

| # | 现象 | 真实根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 导入报 `入库失败：保存失败：写入书籍记录失败` | **事务内 `querySql` 读不到本事务刚写入的行**（铁律 4）。数据其实插进去了，只是回查得 0 | 写入改用 typed `store.insert()` 直接拿 rowId |
| 2 | 任意 INSERT 都报 `SQLite: Abort due to constraint violation` | **设备上的旧库结构过期**：`CREATE TABLE IF NOT EXISTS` 永不修改已存在的表，旧表缺 `format` 的默认值，省略该列时撞上 NOT NULL | 引入 `SCHEMA_BUILD` 编入库名（§5.5） |
| 3 | 第 1 章正文里混进了章节标题 | `start_offset` 被设成标题行首，而非正文首字节 | `start_offset` 指向标题行之后（§5.3 表 2） |
| 4 | 用 `util.TextEncoder` 算字节长度，GB18030 全错 | 该 API 只做 UTF-8（`readonly encoding = 'utf-8'`），且 SDK 无 `StringEncoder` | 新增 `ByteLength` 按编码规则直接计数 |
| 5 | GBK 文件被误判为 UTF-16 | 按 `utf-16le` 解码时大量字节对落进 CJK 区间，得分虚高 | 加"空字节奇偶性"判断，并把 UTF-16 移出打分候选 |
| 6 | `PRAGMA foreign_keys` 查询结果不可靠 | 连接池下读到的可能不是同一连接 | 初始化与每次事务前都设置；改用"插入孤儿行应失败"做确定性验证 |

> **排查方法论的教训**：坑 1 一开始被误判为"`executeSql` 不能 INSERT"、
> "旧库约束"两个方向，各绕了一轮。真正定性的做法是
> **同一次运行内做 A/B 对照（事务内 vs 事务外）**，而不是跨轮次比较 ——
> 跨轮次时库状态、代码版本都在变，结论会互相矛盾。
