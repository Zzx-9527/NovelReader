# 「静读」—— 鸿蒙原生本地小说阅读器 项目说明

> HarmonyOS NEXT 原生应用 · ArkTS/ArkUI 开发 · 完全离线 · 无广告 · 无账号

---

## 一、项目背景

### 1.1 行业现状与痛点

随着网络文学的发展，大量用户养成了在手机上阅读小说的习惯。但市面上的主流阅读类 App 普遍存在以下问题：

1. **广告泛滥**：开屏广告、章节间插广告、阅读界面悬浮广告，严重打断阅读心流；
2. **会员墙与强制登录**：不给权限不让用、不登录不让读，"我自己的书"却要先交出个人信息；
3. **隐私焦虑**：阅读行为是极其私密的个人数据——"我在读什么、读到了哪、什么时间在读"——而主流 App 会将阅读偏好上传云端用于推荐和画像；
4. **格式与编码支持差**：大量用户手中积存着多年的 TXT 小说存档，其中 GBK/GB18030 编码极为常见，很多阅读器打开就是乱码；
5. **大文件体验差**：动辄十几 MB 的单文件长篇 TXT，很多阅读器整本读入内存，打开即卡死闪退；
6. **进度易丢**：换字号、换设备后阅读进度错位或丢失，是阅读器类产品最伤用户的体验事故；
7. **鸿蒙生态缺口**：HarmonyOS NEXT 独立生态落地后，原生应用尚在起步阶段，好用的本地阅读器尤其稀缺。

### 1.2 项目缘起

「静读」正是在这一背景下立项的：做一款**只服务"读自己的书"这件事**的阅读器——用户导入自己保存的 TXT 文件，应用负责把阅读体验做到极致，除此之外不索取任何东西。项目在 HarmonyOS NEXT 上以 ArkTS + ArkUI 声明式开发完成，从文件导入、分章解析、排版分页到阅读统计实现了完整闭环。

## 二、目标用户

| 用户群体 | 典型场景 | 静读提供的价值 |
|---|---|---|
| **本地 TXT 存量用户** | 手机/电脑里存了几十上百本 TXT 小说，长期阅读 | 流畅导入、自动分章、进度不丢、大文件不崩 |
| **被广告与会员墙劝退的用户** | 想安安静静读一本书，不想看广告、不想充值 | 零广告、零会员、零打扰 |
| **隐私敏感用户** | 不希望"我在读什么"被上传或分析 | 零联网，全部数据只留在本机沙箱 |
| **HarmonyOS NEXT 用户** | 新生态内缺少成熟的本地阅读器 | 鸿蒙原生开发，遵循系统设计规范与手势习惯 |
| **注重阅读体验的重度读者** | 对排版、护眼、统计打卡有要求 | 五套主题、精细排版调节、阅读时长统计 |

## 三、产品原则

1. **零联网**：工程内不存在任何网络请求代码，书籍与进度 100% 留在本机；
2. **零注册零广告**：打开即用，没有账号、会员、推荐位；
3. **进度绝不丢**：这是阅读器的生命线——换字号、重启、切后台、换分页模式，都必须回到原来的那句话。

## 四、功能全景

### 4.1 核心功能（P0）

#### ① 书籍导入
- 经系统文件选择器导入 TXT，复制进应用沙箱，之后不再依赖原文件位置；
- **内容指纹（SHA-256）去重**：同一文件不会被重复导入；
- **多编码自动探测**：UTF-8 / GBK / GB18030 / UTF-16 等自动识别，取样前 4 MiB 分析；
- **智能分章解析**：识别"第 X 章 / 第 X 卷 / 序章 / 楔子 / CHAPTER N"等十余种章节规则，记录每章的**字节偏移**而非整章文本；
- **两阶段导入流程**：prepare（解析预览）→ 导入确认页（确认编码、分章结果）→ commit（正式入库）。编码探测置信度低或分章结果可疑时，主动提示用户换编码重解析，而不必重新选文件。

#### ② 书架管理
- 网格（3 列，封面 3:4）/ 列表双视图，可切换并记忆；
- **继续阅读卡片**：顶部常驻最近在读且未读完的书，显示"读到第 N 章 / 共 M 章"+ 进度条；
- 分组管理：新建/重命名分组、移动书籍，分组封面由组内书籍封面拼成 2×2 格子；
- 排序：最近阅读 / 导入时间 / 书名；
- 长按操作菜单：开始阅读、**换编码重解析**（乱码自救）、从书架移除；
- 骨架屏加载、空状态引导、错误状态重试。

#### ③ 阅读器（核心页面）
- **双阅读模式**：滚动模式（整章连续滚动，章末自动衔接下一章）与分页模式（覆盖仿真翻页）；
- **单击三分区**：左 1/3 上一页、右 1/3 下一页、中间呼出/隐藏菜单；
- **独立目录页**：目录 / 书签双 Tab，支持章节跳转；
- 沉浸式全屏：内容延伸至状态栏与手势条区域，按安全区精确避让；
- 屏幕亮度手动调节（-1 表示跟随系统，语义明确）。

#### ④ 阅读进度
- 进度按「章节序号 + 章内 UTF-16 偏移 + 全书百分比」三重记录，**绝不存页码**——页码会随排版变化失效，偏移不会；
- 进度落库 10 秒节流，切后台/退出前强制落盘；
- 重启恢复、换字号后相对位置恢复、滚动位置恢复带超时保护（1.5 秒后放弃恢复、放行进度上报，避免进度被永久冻结）。

### 4.2 增强功能（P1）

#### ⑤ 阅读设置
- 字号（14–30vp 连续滑块，松手才提交防抖）、字体、行距（1.0–2.4）、字间距（0–6）、页边距（0–48）；
- 五套阅读主题：日光 / 暖黄 / 夜间 / 羊皮纸 / 护眼，随主题联动状态栏；
- 翻页方式切换，全部设置持久化到 Preferences（500ms 合并写盘）。

#### ⑥ 书签 / 划线 / 笔记
- 书签、划线（暖黄高亮底纹）、笔记三类标注；
- 标注以「章节 + 章内偏移」定位，与进度体系同一坐标系，换排版后仍准确；
- 目录页书签 Tab 统一管理、跳转。

#### ⑦ 分组管理
- 分组挑选页、分组详情页，分组封面自动由组内前 4 本书封面拼合。

#### ⑧ 阅读统计
- 每日阅读时长（本书 + 全局双维度）、近 7 天柱状图、连续打卡；
- 书架总览：藏书量、总字数、在读/读完数量、标注（书签/划线/笔记）计数；
- 阅读计时带 **5 分钟无操作自动暂停**，不把"亮着屏幕没在看"算进时长。

#### ⑨ 数据备份与恢复
- 导出/导入 JSON 备份文件（带版本号，可迁移）；
- **刻意收窄的备份范围**：只备份用户亲手创造的数据——书签、划线、笔记、阅读进度；
- 恢复采用**合并式**而非整库替换：按书籍 UUID 匹配，标注按"内容+章节+偏移"去重，进度取更靠后的那个——"导出 → 又读了一会儿 → 导入"不会丢任何一边的数据。

#### ⑩ 自检与工具
- 内置 SelfCheckPage 开发自检页，快速验证存储、解析等关键链路。

### 4.3 规划中（P2）

- TTS 朗读（设置层已预留语速/音色/定时关闭字段）；
- 服务卡片「继续阅读」；
- EPUB 格式支持（数据模型已预留 format/metadata 字段）；
- 平板双栏、折叠屏适配。

## 五、技术架构

### 5.1 分层结构

```
pages/          页面层（Index / BookShelfPage / ReaderPage / ReaderCatalogPage /
                ImportConfirmPage / GroupDetailPage / GroupPickerPage /
                ReadingRecordPage / ProfilePage / SplashPage / SelfCheckPage）
views/          视图层（bookshelf / reader / stats / common 可复用组件）
viewmodels/     状态与业务编排（BookShelfViewModel / ReaderViewModel / 刷新注册表）
data/
 ├ service/     业务服务（ImportService / PaginationService / ProgressService /
 │              StatsService / SettingsService / BackupService / ChapterReadService）
 ├ repository/  数据访问（Book / Chapter / Annotation / Stats / Group / PageCache）
 ├ source/      字节源抽象（ByteSource / RawFileSource / FilePickerSource）
 └ database/    RdbHelper（SQLite 建库与升级）
model/          纯数据模型（Book / Chapter / Annotation / ReadingPosition …）
common/
 ├ utils/       工具（EncodingDetector / ChapterParser / StreamTextReader /
 │              HashUtil / ChapterCache / FileUtil / PathUtil / DateUtil / Logger）
 ├ theme/       主题体系（AppTheme / AppFont / ThemeApplier）
 └ constants/   集中常量（AppConstants / DbSchema / DbConstants / SettingsKeys）
```

MVVM 分层：ViewModel 只读服务层产出的数据快照，不接触数据库与 Preferences；服务层保持纯计算可测；页面只做渲染与手势分发。

### 5.2 数据库设计（SQLite，6 张表）

| 表 | 职责 | 关键设计 |
|---|---|---|
| `book_group` | 书籍分组 | 软删除 |
| `book` | 书籍元数据 + 进度 | uuid 唯一锚点、file_hash 部分唯一索引去重、进度三字段（章序/偏移/百分比） |
| `chapter` | 章节目录 | 只存**字节偏移**（start_offset/end_offset），UNIQUE(book_id, chapter_index) |
| `annotation` | 书签/划线/笔记 | 章内偏移定位，外键级联删除 |
| `reading_daily_stats` | 每日阅读时长 | 按书快照书名（书删除后统计仍可读），UNIQUE(book_id, date) |
| `page_cache` | 分页断点缓存 | UNIQUE(book_id, chapter_index, layout_key)，按排版指纹缓存 |

建表语句全部 `IF NOT EXISTS` 可重入执行；外键依赖顺序固定；索引刻意不建与 UNIQUE 重复的冗余项。

### 5.3 关键技术点

#### （1）大文件流式处理
全书**从不整读入内存**。导入时以 1 MiB 分块流式解码（跨块残字节由 StringDecoder 处理），分章解析只记录每章的字节偏移区间；阅读时按偏移**随机读取单章**，单章解码上限 2 MiB，配合 5 章 LRU 正文缓存。十几 MB 的长篇在低端设备上也能秒开。

#### （2）编码自动识别与用户自救
取样 4 MiB 做 BOM + 字符分布检测，输出"编码 + 置信度"。置信度低或分章结果可疑（兜底切分且章数极少 ⇒ 平均十万字一章，几乎必然是编码选错）时，UI 主动引导用户换编码，**一键重解析**而无需重新导入。

#### （3）智能分章算法
十余条高置信度正则规则按优先级匹配（中文卷/章/回、英文章节、序章/楔子/番外等），行级匹配在流式解码过程中完成并同步推进字节游标，保证章节边界**字节级精确**。命中规则不足 3 条时降级为按 8000 字兜底切分，保证任何文件都能读。

#### （4）自研分页引擎
- 以「章内 UTF-16 下标」为断点坐标系，与标注体系同源；
- **排版指纹 `layoutKey`**：字号/行距/边距等参数生成指纹，分页结果按指纹缓存——切回同一章不重算，改排版才失效；
- **算法版本号 ALGO_VERSION**：断点算法变更必须 +1，防止新算法命中旧缓存；
- 实测分页有 6 万字/章上限保护：超限（分章失败的巨型"章"）自动降级为 O(n) 估算分页——"能翻页"远比"每页排得完美"重要，从根上杜绝"正文闪一下然后卡死"的白屏假死；
- 分页测量与正文渲染**强制同源**：字体解析收敛到唯一入口 `resolveFontFamily()`，杜绝"测量用 A 字体、渲染用 B 字体"导致的溢出/裁行。

#### （5）进度体系
进度 = 章节序号 + 章内偏移 + 百分比，与排版彻底解耦；滚动位置恢复采用"onAreaChange 触发 + 延迟重试"双通道，并带 1.5 秒放弃时限保护进度上报闸门；章末自动衔接下一章设 800ms 冷却，防止切章期间旧内容高度误判导致连跳数章。

#### （6）手势与时序细节
长按选中与单击翻页的冲突（400ms 阈值区分）、系统选择菜单浮层与应用弹窗的时序（120ms 延迟避让）、点击与滑动的最小位移阈值（40vp）等十余处交互细节均有明确的量化参数与成因注释。

## 六、特点与创新

### 6.1 产品层面

| 创新点 | 说明 |
|---|---|
| **彻底的零联网** | 工程内不存在网络请求代码，不是"可以离线"而是"物理上不能联网"，隐私保护由架构保证而非由承诺保证 |
| **两阶段导入 + 编码自救闭环** | "探测 → 预览 → 确认 → 可疑主动提示 → 换码重解析"完整流程，直击 TXT 圈 GBK 乱码这一最普遍痛点 |
| **进度与排版解耦的进度模型** | 不存页码存偏移，换字号/换设备/换分页模式后都回到"同一句话"，这是多数阅读器做不好的一点 |
| **可疑分章主动预警** | 从"平均每章字数"反推编码错误的特征，在入库前拦截，而不是让用户打开时白屏假死 |
| **合并式备份恢复** | 按内容去重、进度取更靠后，导出→继续读→导入双向不丢数据 |
| **只备份用户创造的数据** | 书源文件、分页缓存可由用户与系统自管，备份文件小而精 |

### 6.2 工程层面

- **大文件字节偏移寻址**：分章只记偏移、阅读按偏移随机读，内存占用与书的大小无关；
- **分页断点缓存体系**：layoutKey 指纹 + ALGO_VERSION 双保险，缓存正确性与失效完备性兼得；
- **工程化注释文化**：每个"魔法数字"都有集中定义，且每个非常规取值都写明"为什么是这个数、踩过什么坑"（如 400ms 单击阈值、0.92 字宽比、6 万字测量上限），形成可传承的决策记录；
- **严守 MVVM 边界**：ViewModel 不碰 IO、服务层纯计算可测、模型纯数据，ArkUI 装饰器限制（如 ForEach key 生成规则）作为经验沉淀在模型层统一收口；
- **零敏感权限**：不给应用任何文件全局读写权限，文件访问全部经系统选择器临时授权，权限模型最小化。

## 八、隐私与安全声明

- **不联网**：无任何网络权限与网络请求代码；
- **不采集**：无账号体系、无埋点 SDK、无第三方统计；
- **最小权限**：不申请存储等敏感权限，书籍文件经系统文件选择器读入沙箱；
- **数据归属**：全部数据（书、进度、标注、统计）存于应用沙箱，用户可随时通过备份功能导出 JSON 自行保管，卸载即彻底删除。

## 九、总结与展望

「静读」以"读自己的书"为唯一使命，用鸿蒙原生技术栈完成了一个从导入、解析、排版、阅读到标注、统计、备份的完整闭环。它的核心竞争力不在于功能列表的长短，而在于三条原则的彻底执行——**零联网、零广告、进度绝不丢**，以及围绕大文件、多编码、进度保真这些真实痛点做出的系统性工程投入。

后续规划按优先级推进：TTS 朗读与服务卡片（P2）、EPUB 格式支持、平板与折叠屏多端适配、分章规则的自定义扩展。产品定位始终不变：**做一个安静、可靠、尊重用户的本地阅读器。**
